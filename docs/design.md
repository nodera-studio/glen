# glen v0.2.0 design

Status: v0.2.0 design, written in v0.2 W0 on top of the v0.1.0 design (released as v0.1.0 and v0.1.1). Supported omp range: **18.14.0 to 18.16.0** (tested **18.14.0**, declared in `src/omp/compat.json`, §A19).

glen uses three channels: a read-only disk reader discovers sessions and reads transcripts; an RPC driver runs omp in a detached worker for each job; a bundled omp extension routes requests into live sessions and carries replies back. The channels share a single CLI and versioned output contract.

## §A1 Scope and non-goals
- v0.1.0 and v0.2.0 support **macOS and Linux**. Windows is out of scope: the lease probes and unix sockets are Unix-only, and that code is `#[cfg(unix)]`.
- glen never writes, renames or deletes omp session files. It never takes omp's `.<file>.jsonl.lock.os` append gate, and it never creates files inside omp's directories. The exception is `install-extension`, which writes `<agent_dir>/extensions/glen/` on explicit request.
- No MCP server in v0.1.0; v0.2 W5 adds `glen mcp`, a local stdio server over the CLI (§A22). No network access.
- Not listed in v0.1.0 or v0.2.0: archived sessions (`archive/sessions/*.jsonl.gz`), subagent transcripts (nested `<stem>/*.jsonl`) and collab replicas.
- v0.2.0 adds a supported omp range with capability checks and a nightly run against the latest omp (§A19), replies that reach the calling agent without a polling loop (§A20), an opt-in warm worker (§A21), an MCP layer generated from `docs/json.md` (§A22), and a spike of `omp acp` (§A23).
- Out of scope for v0.2.0 (owner): worktree or parallel-agent orchestration, a cross-harness mailbox, remote or phone access, and A2A over HTTP. glen borrows only A2A's task-state names (§A7).

**Session controls (W3b).** `rpc-mode.ts` implements `abort`, `get_available_models`, `set_model {provider,modelId}`, `get_available_thinking_levels`, `set_thinking_level {level}`, and `compact {customInstructions?}`. Ordinary commands are serialized: abort does not overtake a registry refresh or compaction. Only prompt/steer/follow_up and a few side channels bypass that queue.

`ModelControls.setModel` appends a default-role `model_change` even when unchanged, requires auth, re-applies thinking, and records model usage. `setThinkingLevel` clamps to model capabilities and appends `thinking_level_change {thinkingLevel,configured}` only when the effective level changes. RPC and the extension do not pass persist; global settings stay unchanged. Resume restores the last default-role (or absent-role) model change on the active branch; assistant provider/model is only a fallback before an explicit default, excluding `<synthetic>`. The last thinking change carries configured; no thinking entry means the level comes from settings/model defaults, so disk reporting is null.

Manual compaction aborts and later resumes a running turn. Explicit abort cancels manual compaction but keeps queued steer/follow-up messages queued without starting them. `ctx.isIdle()` only reflects streaming, so glen separately tracks compactions it starts. Session files are lazy until the first assistant answer; earlier model/thinking changes are in memory. `--no-session` creates an in-memory session and cannot combine with resume.

The extension uses `ctx.abort/isIdle/hasPendingMessages/compact/getContextUsage/model/models.list`, and `pi.setModel/getThinkingLevel/setThinkingLevel`. `ctx.models.list()` uses available models without RPC's enabled-model filter; supported levels are off plus thinking.efforts only for reasoning models.

## §A3 The three channels
**Disk reader (W1)**
- **Discovery.** Buckets are the immediate subdirectories of `sessions_dir`. Session files are `<bucket>/*.jsonl` with a valid header. Skip dotfiles (`.lock.os`, `.*.tmp`), symlinked buckets and everything inside subdirectories. Follow symlinked regular files and deduplicate canonical paths. Header scanning falls back from 4 KiB to at most 64 KiB when no complete header fits.
- **Bucket for a cwd.** Port `getDefaultSessionDirName` (`CA/session/session-paths.ts`). Canonicalise the cwd. Canonicalise home and the temp root too (falling back to lexical absolute paths when unavailable). The temp root (`TMPDIR` → `TMP` → `TEMP` → `/tmp`) is checked first (`-tmp-<rel>`), then home (`-<rel>`), else `--<abs>--`. Separators `/ \ :` become `-`.
- **Listing** reads a 4 KiB head and a 32 KiB tail per file, as omp does. `show`/`tail` read the whole file.
- **Parsing:**
  - An optional title slot on line 1 is folded into the header.
  - The first logical line must be `type:"session"` with a string `id`; otherwise the file is not a session.
  - Malformed lines are skipped and counted (`skipped_lines` in JSON). An entry line that fails to parse only because of an unpaired `\uD800`–`\uDFFF` escape is retried once with U+FFFD in its place.
  - If the active-branch walk stops at a missing parent while lines were skipped, `show`, `tail` and `tail -f` warn `branch_truncated` ("N earlier entries may be hidden by a malformed line"); glen never guesses the missing ancestors.
  - A session file or bucket directory that cannot be read (any error but not-found) is left out of the catalog and warns `unreadable_session` in `ls`, `show`, `tail` and `tail -f`. A lookup that misses while such paths exist fails `io` naming the path, with `details.unreadable`, rather than `not_found`.
  - Unknown entry types are kept as opaque tree nodes (id/parentId), so the parent chain stays intact. They are never rendered except with `--raw`.
  - Unknown fields are ignored. Unknown content blocks render as `[<type>]` in human mode and pass through with `--raw`.
- **Leaf.** If the last entry has `activeLeafId`, that is the leaf (`null` = empty). Otherwise the leaf is the last entry's id. A captured leaf id that no longer exists falls back to the newest entry that selects itself.
- **Active branch.** Walk `parentId` from the leaf, stopping on a repeated id, then reverse.
- **Rendering:**
  - Shown: `message` by role (user, assistant, toolResult, developer, bashExecution, pythonExecution, custom, fileMention); `custom_message` with `display:true`; `branch_summary`; `compaction` and `reset_boundary` as dividers; `model_change` and `thinking_level_change` as muted meta lines.
  - Thinking is hidden by default (`--thinking` shows it). Tool calls are collapsed by default (`--tools`).
  - Everything else is hidden unless `--raw`.
- **Continuations.** Port `findSessionContinuation`: follow files whose header `continuationOf` names the session, recursively, and take the copy that holds the newest turn. JSON reports `continued_from: [ids]`. Never follow a fork (`parentSession` without `continuationOf`).
- **Liveness** is a read-only probe of `<session_owners_dir>/<name>.lock`:
  - The `.lock` suffix is appended by `file-lock.ts` `getLockPath`, not in `session-storage.ts`; see §A2.
  - `<name>` is the header's session id when it matches `^[A-Za-z0-9_-]{1,128}$`, which every uuid does. Any other id is named `h-` + `Bun.hash.wyhash(id)` in 16 hex digits. glen does not port wyhash in v0.1.0, so such ids probe as `unknown`.
  - The path is the lexical absolute string omp would produce (`path.resolve`: no symlink resolution, no realpath).
  - macOS: open the file *without* `O_CREAT`. ENOENT → not live. `flock(LOCK_EX|LOCK_NB)`: EWOULDBLOCK → live; success → unlock at once → not live.
  - Linux: bind the abstract DATAGRAM socket `omp-file-lock-` + XXH64(path, seed 0x4f4d502d4c4f434b) hex16 + XXH64(path, seed 0x50492d46494c454c) hex16, where path is the UTF-8 string above. The hex is lowercase and zero-padded. EADDRINUSE → live; success → close → not live. This is a bind, never a connect, and never a stream socket.
  - Any other error → `unknown`, including EACCES/EPERM: a permission error is never evidence that the lease is free.
- **State column.** `idle|live|busy|unknown`, with `state_source:"disk"` in W1 (W3 adds `"extension"`) and nullable `state_detail`. A free lease means idle; an inconclusive probe means unknown. A held lease means busy when the last active-branch message is in flight: role user, developer or toolResult, or an assistant containing a toolCall whose stopReason is neither error nor aborted. Otherwise it means live. This predicate is separate from the last-turn state `complete|interrupted|aborted|error|pending|unknown`, ported from `session-listing.ts`.
  - If a held session's 32 KiB tail window contains no complete message, load its full active branch to determine state and last turn. Other rows retain bounded scans.
  - Probe only displayed rows, except when `--live` needs to filter candidates. A probe briefly holds a free lease; never repeat it inside the follow loop. Linux abstract sockets are network-namespace-local: a probe in another netns cannot observe the owner's socket.
- **Follow.** `tail -f` polls file metadata every 250 ms and complete appended lines only; a partial line waits for its newline. Check continuations every 2 s or immediately after disappearance. A missing file with no continuation for 5 s ends with `not_found`.
  - A size shrink or changed device/inode triggers a reload and `rewritten`, including omp's stage-and-rename replacement by a larger file. Every poll also checks the last 4 KB already read; the full read-prefix hash runs only after size or mtime changed, and at most once every 5 s. Emit only unseen active-branch entry IDs after a rewrite or continuation; when omp migrates a followed v1 file to version 3 (in place or as a continuation), it gives every entry a fresh random id, so the v1 entries already emitted are matched to the migrated entries by position, stopping at the first entry whose kind, timestamp, role or content differs, and only the entries after them are emitted; report `branch_switch` when the previous leaf is no longer on the branch.
  - Polling avoids platform-specific FSEvents/inotify dependencies and survives replacement. Same-size title-slot edits intentionally do not trigger a reload. SIGINT ends the stream with `end` and exit 130; a second SIGINT exits 130 immediately.

**RPC driver (W2)**
- `omp-rpc` is pinned to git tag `v18.14.0` (not a path dependency).
- **Per-job detached worker.** `send` creates a durable job, then re-execs hidden `glen __worker <job-id>` in its own session (`setsid`), with stdin `/dev/null` and stdout/stderr to private `worker.log`. Neither it nor omp inherits the foreground pipes. Foreground observers never cancel the worker on Ctrl-C.
- **Worker lifecycle:**
  1. Claim the queued job with `worker_pid` and its process start token; register SIGTERM/SIGINT/SIGHUP cancellation.
  2. Hold glen's per-session flock through teardown. Poll every 200 ms while queued, checking abort and the absolute job deadline. Re-follow continuations after acquiring it; refuse a moved id with `session_moved` before starting omp.
  3. Probe the owner lease using the `owners_dir` frozen in `job.json`; held or unknown becomes `no_route`.
  4. Start `omp --mode rpc --no-ui [--profile NAME] [--resume <absolute file>]`, `GLEN_MANAGED=1`. An explicit profile removes `OMP_PROFILE` and `PI_PROFILE` from the child environment; otherwise both are inherited. Resume uses an existing header cwd, falling back to glen's cwd; `@new` uses `--cwd` or glen's cwd.
  5. On a startup thread, wait for ready, register exactly one `glen_reply` host tool, set the event allowlist, then take a `get_state` baseline. The main thread polls controls and the deadline every 200 ms. Cancellation sets a shared abandon flag and writes terminal status plus the control acknowledgement immediately, then joins startup. Startup checks abandon after every call, drops any late client, and never prompts an abandoned job. Worker exit waits for teardown and the join.
  6. Refuse a baseline id mismatch (`session_moved`); for `@new`, acquire the glen lock for the revealed id. Re-check cancellation/deadline and discard startup events. Do not re-probe our own child’s lease: startup recovery may already have claimed it.
  7. Submit a prompt on a scoped thread under the cancellation mutex, with a 100 ms ack wait. Read the SDK event receiver directly on the polling loop; drain it before finalization so pre-ack output cannot lag behind completion. A late ack still arrives as an unmatched response. The first session event or completed outcome writes `accepted`. The event filter excludes message/tool streaming updates while retaining terminal messages and notices.
  8. Complete on a completed `prompt_result` with `sessionSettled:true` or an observed post-prompt `session_settled`. An ack with `agentInvoked:false` completes locally without waiting for either; preserve `command_output`. A completed result frame with `agentInvoked:false` and an unsettled session waits at most 10 s, then completes with `settle_timeout`. Cancellation after a completed result preserves completion with `session_settled:false` and `settle_cancelled`. EOF after an unsettled completed result ends the wait immediately with `settle_timeout`; reconcile any outstanding prompt acknowledgement before treating EOF as failure. `final:true` replies never complete a job.
  9. On every completed outcome, recheck identity with a separate 1 s budget (including completed-unsettled deadline and cancellation paths); skip this check for aborted or failed outcomes. Write `result.json` before terminal `status.json`, answer controls, close the client, then release the glen lock — unless the worker stays warm (§A21, v0.2 W4), which defers closing the client and releasing the lock to its own idle loop and one teardown. `Client::close` terminates omp's private process group. Background commands the bash tool placed in separate groups can survive; glen does not hunt them.
- **Fork detection.** Re-read `get_state` on persistence notices, changed `session_info_update` ids and before finishing. A change from the baseline records `{from,to}` and returns exit 11 with both ids and `to_handle`; never infer ids from notice prose. Tag running queries with increasing sequence numbers and ignore older results after a newer identity was applied. Unmatched responses from timed-out state calls cannot publish identity. Before recording a `glen_reply`, resolve identity through a fresh bounded state query on the worker, so a reply arriving during a fork query cannot enter the old inbox. Persistence errors add a warning.
- **Pre-spawn probe (AC-207, revised for W2 review cycle 1).** When the glen lock is free, `send` re-probes the owner lease after reading stdin; held or unknown refuses with exit 6 before creating state, unless a fresh glen-lock check now finds a worker to queue behind. The worker probes again immediately before spawning; held or unknown fails `no_route` without prompting. There is no pre-prompt probe: omp startup recovery writes can claim our own child’s lease before ready. Baseline identity checks and post-start fork detection remain mandatory. This supersedes the two-probe AC-207 in the original W2 plan.
- **Timeouts:**

| Bound | Value | Outcome |
|---|---|---|
| Foreground send/wait | default 90 s, 0 for no-wait | exit 10; worker continues |
| Null worker pid | 10 s spawn grace | reader persists lost |
| Absolute job deadline | `GLEN_JOB_TIMEOUT`, default 60m, from creation | queued/startup: failed timeout; running: abort; completed-unsettled: completed with `settle_timeout` |
| Owner lock wait | until job deadline, 200 ms polling | timeout or cancellation |
| Ready | min(60 s, time left) | startup unavailable; abandoned startup joins before exit |
| Setup calls | 10 s each | per-call error mapping |
| Running state calls | off the polling thread; at most min(10 s, time left) | terminal status precedes a pending-call join; every completed outcome awaits a separate 1 s final identity check |
| Abort calls and prompt ack | 100 ms each | late responses read from the event receiver; controls stay responsive |
| Prompt result | absolute job deadline | polling loop aborts when the deadline passes |
| Abort escalation | 10 s then SIGTERM; SIGKILL 1 s later | event receiver closes on EOF |
| Client teardown | SIGTERM, 1 s; SIGKILL, 1 s; bounded reader join | log teardown errors |

- Tests use the `fake_omp` example, never live omp (§A15).

**Live route (W3)**
- The single-file, erasable TypeScript extension (`extension/glen/index.ts`) uses only `node:` runtime imports. omp runs it with Bun; Node ≥22.6 runs its tests. `install-extension` embeds and renders it with an absolute GLEN_HOME and version. Runtime `GLEN_HOME` overrides the baked home; `~` expands. A process-wide `Symbol.for("glen.extension")` guard suppresses a second installed/`-e` copy, while the same module can rebind for subagents.
- `GLEN_MANAGED=1` registers **nothing** (no tool, handlers, endpoint or files). Otherwise the factory registers `glen_reply` with `loadMode:"essential"`, `approval:"read"` in every mode. Only a main-agent `session_start` in mode `tui` binds an endpoint; subagents and RPC/ACP/print hosts never bind one.
- Bind lifecycle: require an absolute home and a plain-token session id (`^[A-Za-z0-9_-]{1,128}$`); create `run/live` 0700, sweep dead-pid registries/sockets, unlink the process's leftover socket, bind `<pid>.sock`, chmod 0600, then atomically publish `<lock_key(sessionId)>.json` 0600 **before the handler resolves**. Registry fields: `{v:1,pid,session_id,session_file:null|string,socket,ext_version,omp_version:null|string,protocol:1,mode,started_at,cwd:null|string}`. Optional title is understood by Rust. Version import has a managed 500ms cap. No omp transcript or append gate is ever opened for writing.
- Every client connection checks the socket's kernel peer before it writes a byte: the registry's pid, this user, and confinement ordering (§A14 S-18).
- The resolver unions endpoint-only sessions with the disk catalog, assigning handles across both. They are addressable by id, handle and `@latest`, and appear in `ls` with `state_source:"extension"`. `show`/`tail` return an empty transcript and `not_yet_persisted`; `tail -f` waits for persistence. This is added **AC-326** (orchestrator O3). A missing cwd uses the invoking project for catalog scope.

- Unknown fields and unknown client event kinds are ignored. Malformed JSON, invalid UTF-8, missing string id or oversized request returns `bad_request` (unknown id null). Duplicate held/settled request ids are rejected before injection (bounded settled-id history). Session mismatch never injects.
- **Delivery:** idle means `pi.sendUserMessage(text)` with no options, for every requested delivery mode (ack `prompt`). Busy steer uses `{deliverAs:"steer"}`; busy auto/follow_up uses `{deliverAs:"followUp"}`. Explicit delivery queues even when idle, so glen never supplies it while idle. `sendUserMessage` returns void.
- **Consumption and attribution (O6 amendment):** push each request before injection and buffer synchronous events until the acknowledgement. Only `message_end` with role `user` and text equal to one pending injection consumes it, in submission order; record the event sequence as its consumption identity. `agent_start` and joined `before_agent_start.prompt` never prove delivery. One boundary can consume at most one request. Replies and assistant messages belong only to the currently open request span; a user message always clears prior ownership (except adjacent queued requests in the same batch), while custom/developer/system/async-result notices clear it only after the span contains assistant text; before that, the waiting span retains ownership. Disconnecting retains the span and durable inbox delivery.
- **Settlement:** close the current span as soon as the next user message starts, regardless of whether it has an answer, except for adjacent queued glen requests sharing the same batch (`message_end` is the fallback for hosts that omit starts). A custom/async-result/system-notice message (including other non-assistant/non-toolResult notice roles) closes the span only if it already contains assistant text; otherwise the span continues past the notice, retaining ownership until its answer arrives. Assistant starts, tool-only assistant messages and `glen_reply` records do not count as assistant text for this rule. A last span closes when the terminal main-agent `agent_end`'s managed 50ms poll observes idle and no pending messages, bounded at 30s and invalidated by a later agent start or pending messages; a later terminal end re-arms it. Never settle an unconsumed request as completed: an undelivered submission has a 30s delivery deadline, and an unconsumed queued message at quiescence fails `not_delivered`. Delivery timers are cancelled on consumption or termination.
- Assistant text is the last assistant text inside the span. Assistant text/stopReason/errorMessage come only from assistant `message_end` inside that request's span, never from `agent_end.messages` or a later request's assistant output. Text blocks join with newlines; an empty/tool-only span gives null text. `aborted`/`error` stopReason maps to those states; everything else completed. The Rust live driver uses the per-request `settled` event unchanged as the job's result source.
- **Identity:** every main event and socket request compares the current session manager id/file. Publish the new registry before pid-checked removal of the old one. Emit `session_changed`, reason `new|resume|fork` from session_switch, otherwise `moved`. The `session_switch` event terminates old requests on new/resume with `session_switched`, even if hello/state already refreshed the cached id in the event gap; requests submitted for the new id in that gap survive; moved/fork remain observed and report exit 11. A non-token id unregisters and terminates requests.
- **Cleanup:** shutdown emits `error shutdown`, closes the server and unlinks its socket and pid-owned registry synchronously within omp's 2s budget. A synchronous process exit backstop repeats the unlinks. Raw callbacks are guarded, socket/server errors have listeners, timers use the managed ctx API (socket idle timeout is the Node socket API). No terminal output; TUI notices use `ctx.ui.notify`.
- `GLEN_EXT_TRACE=<absolute file>` appends guarded NDJSON event/flags/idle/queue/request state snapshots. Step 5 failed attribution under the original idle-only rule; the O6 amendment above supersedes it. **Watch (W5)**
- Four long-lived readers own their I/O and caches and send messages to the UI; the reducer and view do no I/O. Sessions refresh every 2s, or immediately on refresh/scope changes. Follow polls every 250ms. Jobs refresh active statuses every 250ms and list the store every 1s. Inbox reads new records every 500ms and re-reads persisted cursors every 1s.
- **Probe on change.** A disk row with a previously free lease skips the next probe while its device, inode, size and mtime are unchanged. Changed files, held leases and unknown leases are probed again; matching extension-backed rows are never probed. Head and refined-tail caches avoid rescanning unchanged files.
- **Shared cores.** Watch reuses `tail -f`'s `Follower` and `send`'s `submit` path; the extraction preserves CLI output byte-for-byte and retains the same routing/refusal behavior. The transcript updates per persisted entry, not per token; partial lines wait for their newline.
- **Peek-only inbox.** Watch never marks replies read or writes `inbox/.read`; persisted cursors only inform unread counts.
- **Controls.** Watch's `m`, `T`, `C` and Ctrl-X controls dispatch through `src/ctl`, the same routing as the CLI controls. The “session controls are not in this build” toast is only a fallback.

## §A4 Routing (`glen send`)
1. Resolve the target including endpoint-only sessions, follow continuations, read/validate text. Target resolution for send does **not** probe the lease. `@new` always uses RPC.
2. Before consulting either lock, inspect `run/live/<lock_key(id)>.json`. A 2s matching hello with protocol 1 and send in ops selects live; no omp binary or owner-lease probe is needed. If the glen session lock is also held, refuse exit 6 with `glen jobs --active --session <handle>` guidance. Extension version mismatch warns with both versions and still routes live.
3. Dead pid, missing/refused socket or a hello naming another session: rename the registry to a unique hidden tombstone, verify the captured identity, then delete; restore a changed registry with a create-only hard link and fail closed if cleanup races; remove its socket only when the pid is dead, then continue. Unreadable registry, oversized socket path, timeout/malformed hello or missing capabilities: fail closed with exit 6 **before creating a job**, with install/restart guidance (shorten GLEN_HOME for the path case). An untrusted endpoint (§A14 S-18: a socket other than a private `run/live/<pid>.sock`, a kernel peer or hello pid other than the registry's, or a peer more confined than glen) fails closed the same way with `untrusted_endpoint`, and nothing is cleaned up.
4. Without a live endpoint, a held glen lock selects queued RPC, preserving W2 queueing. Otherwise probe the owner lease: free selects RPC; held refuses with `run glen install-extension, then restart that omp session` when absent, or `restart that omp session so it loads the glen extension (only TUI sessions accept glen messages)` when installed. Unknown refuses.
5. Only RPC/new resolves omp. Its worker re-checks the endpoint before the pre-spawn lease probe and again **endpoint-only** immediately before prompting. An answering or unhealthy endpoint fails no_route without a prompt; no RPC-to-live handoff is attempted. Startup recovery can claim the child's own lease, so no second lease probe is safe.

The worker passes the caller's environment through to omp, subject to the explicit-profile scrubbing in §A3; the harness relies on inherited `PI_CONFIG_FILES`, pinned by `tests/rpc.rs::w9_send_passes_profile_and_config_overlay_env`.

**Residual race.** The extension closes the idle-TUI gap for resumed and brand-new TUI sessions before their first write. An unextended TUI can still open between a lease probe and first RPC write; the RPC path narrows that race and reports a detected fork as exit 11. `show`/`tail` retain W1's brief read-only lease probe and never route. Endpoint-only targets cannot fall back to RPC until a transcript exists.

### Controls (W3b, AC-351–369)
`abort` (visible alias `stop`), `model`, `thinking`, and `compact` route endpoint → lock-holding RPC job → unowned short-lived RPC. They follow W4's sandbox order: refuse_unreachable, live endpoint, then refuse_rpc. A responding endpoint plus a held glen lock, an unhealthy endpoint, or an owner lease held/unknown without an endpoint refuses exit 6 before a control file or process is created. Old extensions get details.reason extension_outdated, ext_version, and install/restart guidance. A free, unowned idle abort returns route none and creates nothing.

A held lock whose holder is an idle warm worker (kind `warm`, v0.2 W4, §A21) is not routed to directly: `abort` treats it as idle without cooling it; every other control writes a release request addressed to that holder's own identity, waits until the lock frees (or a new holder appears), and only then continues the loop — so a warm session is otherwise routed exactly as a free one.

The RPC client acquires and marks the glen lock, re-follows continuations, checks endpoint and lease immediately before spawn, and reroutes once if an endpoint appeared. It starts `omp --mode rpc --no-ui [--profile P] --resume FILE`, GLEN_MANAGED=1, in the session cwd when it exists. Glen owns the child before starting the RPC handshake; startup cancellation or failure terminates its process group with TERM then KILL, reaps the leader and confirms the group is empty before releasing the lock. A baseline id mismatch is control_failed/session_moved before any operation. Re-read state after the op, report forked exit 11, close omp, then release the lock. Child stderr is piped and drained; successful controls include up to 16 omp_stderr warnings, each capturing at most 1024 bytes of a line, without writing to glen's stderr. glen never appends the transcript. Persistence error notices produce persistence_error warnings. The extension-less TUI race remains: before its first write it may hold no lease, retain an old in-memory model, and later write beside a control entry; equipped TUIs close this window.

`models` never resumes a session: use live list_models or its owning job; otherwise start a throwaway `--no-session --no-extensions --no-skills --no-rules` client in a private, empty 0700 scratch directory and obtain current selection from the active disk branch (v0.2 W6, security audit S-02); a side effect is that `models` no longer lists a provider only an extension would have registered. Unreachable sessions warn session_unreachable; outdated extensions warn extension_outdated. Endpoint-only fallback has null selection/current_source and not_yet_persisted. Without a target current is null and default_model names the in-memory default. Lists are sorted, provider-filtered before total, and create no GLEN_HOME except output spill. Sandbox refusals still follow W4.

Every command has a positive --timeout DUR, default 90s. Hello ≤2s, live abort ≤4s (extension settle ≤3s), other live ops use remaining time. RPC ready ≤min(60s, remaining); list/model calls ≤30s, thinking/state ≤10s, compact bounded by the command. Deadline, SIGINT, SIGTERM or SIGHUP stops an RPC process group with TERM/KILL, never an abort queued behind compact, and exits within 5s; each signal gives the interrupted outcome (exit 130), and a repeated SIGTERM or SIGHUP exits at once with 143 or 129. Live stops close the socket with a may-still-finish hint; job stops report unknown outcome and the job handle. Re-route once after job_ended. A model, thinking or compact change that succeeds after the deadline keeps its result and adds the top-level warning `deadline_passed_after_apply`. If omp goes away after glen submitted a change, the control fails `control_failed`/`outcome_unknown`: the change may have been applied.

## §A5 Reply channel (`glen_reply`)
- **Consumption identity, omp 18.14.0:** `CA` below means `packages/coding-agent/src` in the read-only reference clone. `CA/extensibility/extensions/types.ts:2062` declares `sendUserMessage(...): void`; `loader.ts:349-350` and `runner.ts:1597-1598` forward that void call, so no returned message/entry id or promise is available. `CA/modes/controllers/extension-ui-controller.ts:1494-1499` catches the asynchronous session submission error and only reports it to the TUI; the extension receives no submission-error event, so glen uses the delivery timeout. `CA/extensibility/extensions/types.ts:1211-1218` exposes a detached `message_end.message`, mirrored by `lifecycle-mirror.ts:142-152`. The user message type (`packages/ai/src/types.ts:1188-1205`) has content/timestamp but no entry id. Therefore glen uses exact user text plus pending-injection order and the observed event sequence; identical texts consume one pending request at a time. This cannot distinguish an independently typed identical message, a limit of omp's exposed identity, but unrelated runs and substring matches cannot consume a request. Input boundaries arrive as start/end pairs (`packages/agent/src/agent-loop.ts:1154-1158`); queued user content preserves its text (`CA/session/agent-session.ts:9480-9484`), and explicit send delivery queues before returning (`10299-10304`).
- **Tool** `glen_reply`, params `{text: string, final?: boolean}`. Description: "Send a message back to the agent that contacted you through glen (Claude Code or Codex). Use it to answer a glen request or report progress." It returns `"delivered"`.
- **Exactly one provider per omp process.** omp rejects a host tool whose name an extension already registered.
  - glen's RPC children run with `GLEN_MANAGED=1`; the extension skips its tool and socket there, and the worker supplies a host tool via `set_host_tools`.
  - TUI and print sessions with the extension installed use the extension's tool.
- **RPC host-tool approval:** RPC host tools carry no approval tier in omp 18.14.0 (`RpcHostToolDefinition`, `CA/modes/rpc/rpc-types.ts:866-876`; wrapped at `CA/session/session-tools.ts:2600-2607`). Under a non-yolo `tools.approvalMode`, `glen_reply` in an RPC job fails closed unless the profile sets `tools.approval.glen_reply: allow`. Approval prompts fail closed only because glen passes `--no-ui` (`CA/main.ts:2807`).
- **Delivery:**
  - RPC: append in call order to `jobs/<id>/replies.ndjson`, then the inbox, and include the same records in `result.json.replies`. A job append error returns a tool error without an in-memory record; inbox errors are logged and the job reply is retained.
  - Live: the extension streams a `reply` event to a connected worker (when a glen request is active) and appends to `inbox/<sessionId>.ndjson`: `{v:1, id, session_id, job_id|null, request_id|null, tool_call_id|null, text, final, at}` — every field is always present; absent values are `null`, never omitted.
- Extension replies reach the inbox only through the extension; the Rust live worker writes job replies/results only. The extension tool does synchronous private file I/O and never waits for a peer or performs network I/O. Registry refresh is best-effort and logged through trace/TUI notification; its failure cannot prevent inbox append or successful tool delivery. If both inbox append and streaming fail, it returns isError.
- Human `glen_reply` call rows summarize reply text as `↳ glen_reply "…" · ✓ delivered`, truncated to width; JSON retains the existing raw-arguments contract (**AC-327**, O8).
- **Validation:** text must be a string, nonempty after trimming, at most 65,536 UTF-8 bytes; optional `final` must be boolean. Invalid calls record nothing and return a tool error. `final:true` is data only, not completion. W2 writes the private inbox; reading it ships in W3.
- **Reading:** `glen inbox` shows unread messages, tracked by a per-session byte-offset cursor in `inbox/.read/<sessionId>`, and marks them read unless `--peek`. `--follow` streams NDJSON. Two receivers return when a reply lands, so no agent polls (v0.2 W2, §A20): `glen wait <job> --for reply` for a job's replies and `glen inbox --wait` for late and TUI messages.

## §A6 glen state (`GLEN_HOME`)
```
$GLEN_HOME            default ~/.glen; must be absolute; leading ~ expanded; relative → invalid_env (exit 2)
├── run/live/<lock_key>.json, run/live/<pid>.sock    W3 live endpoints
├── run/warm/<lock_key>.{json,release,lock}     v0.2 W4 warm worker (registry, release request, metadata lock)
├── run/locks/<key>.lock                        W2 per-session request lock
├── jobs/<jobId>/{job.json,status.json,result.json,worker.log}   W2
├── jobs/<jobId>/replies.ndjson, control/<name>.{json,done.json}   W2
├── inbox/<sessionId>.ndjson                                    W2/W3 writes
├── inbox/.read/<sessionId>                                     W3 reads
└── out/<unix-ms>-<command>-<pid>.{json,txt}                      W0 spilled output
```
- **Lock keys:** a plain token session id is its own key; other ids use `h-<xxh64(id,0)>`. These are glen locks, never omp append gates. Lock files are never unlinked.
- **Modes:** directories glen creates are 0700, files 0600. glen never chmods a GLEN_HOME that already exists; doctor warns about group/other bits.
- **Trust (W8 SEC-3):** before writing, glen checks GLEN_HOME and each existing directory on the way to the write: each must be a real directory (not a symlink), owned by the current user, with no group or other write bit. A missing directory ends the check and is created 0700. Otherwise glen refuses with `invalid_env` (exit 2), the path, and the hint `point GLEN_HOME at a private directory you own (mkdir -m 700)`; writes that flatten their errors (output spill, RPC replies) report the same refusal as `io`, and a control request written to a job's control inbox reports it as `control_failed`. Nothing is created inside a refused home: the check runs before and after the directory is created. A 0755 home is accepted. Lock files open with `O_NOFOLLOW` and must be regular files owned by the current user. Reads are checked too: `send` and the session controls check `run/live` (and `jobs`) before they trust a live registry, `jobs`, `wait` and the control job lookup check `jobs`, `inbox` checks `inbox/.read`, and `watch` checks all three, each refusing with `invalid_env` like a write. The extension applies the same rules to GLEN_HOME, `run` and `run/live` at session start: on a violation it binds no socket, writes no registry, and tells the TUI that live delivery is off. `glen_reply` checks GLEN_HOME and `inbox` the same way before it appends, opens the inbox file with `O_NOFOLLOW`, and fails the tool call with the refusal instead of writing.
- **Atomic writes:** a temp file in the same directory, then rename.
- **Inbox cursors:** `inbox/.read/<stem>` contains `{v:1,offset,ino}` (0600; .read 0700). Restart from zero on inode change or truncation. Only complete lines are consumed; malformed lines count as skipped. When a cursor will move, first probe that the marker directory is writable (a dotfile opened `O_NOFOLLOW`, then removed); if not, print only the mapped error (exit 6 `sandboxed` in a Codex sandbox, otherwise `io`) and leave the messages unread. Commit cursors only after successful output and flush. `marked_read` is true only when a cursor moved, so `--all` with nothing new writes nothing. Appends (the extension's inbox and glen's job files) first add a newline when the file ends in a torn line, so a crash mid-write costs one skipped line, not the next record.
- **Socket paths:** counted in UTF-8 bytes, paths ≥104 on macOS or ≥108 on Linux are refused. Install still succeeds with socket_path_too_long; doctor warns; send fails closed. Shorten GLEN_HOME.
- **Retention:**
  - On every spill, `out/` entries older than 7 days are pruned, but only regular files with glen's spill name (`<digits>-<command>-<digits>.json|txt`) owned by the current user; anything else in `out/` is left alone.
  - Only terminal jobs (including lost) whose parsed status `updated_at` is more than 7 days old are pruned when a new job is created. Active or unreadable jobs are kept; pruning is best effort.
  - Inbox files are kept.

Lock holder records (W3b) are written on the held inode with ftruncate/pwrite: `{v:1,kind:"job"|"control"|"warm",job_id:null|string,pid,start:null|string}` (`"warm"`: v0.2 W4, §A21). Trust only a held lock plus a matching live pid/start; job holders must belong to that session and remain non-terminal. Poll up to 1s, then use a single active, non-waiting, live job as the older-worker fallback. Unknown/control holders make other controls wait with 200ms polls; abort returns busy. A `warm` holder is reported idle only while no active job of the session already names its pid (the claim write flips the holder to `job` first, so this is only the flip's microsecond window). Lock files are never unlinked.

## §A7 Jobs
- **Id:** glen uuidv7; **handle:** `j` + last 7 hex. `wait` accepts a full uuid or `j` plus at least 7 hex suffix digits, case-insensitively. Multiple matches return `ambiguous` with candidates; bad shapes return usage with a `glen jobs` hint.
- **`job.json`:** `{v,id,handle,created_at,route,session_id?,session_file?,session_handle?,deliver_as,text,cwd,omp_bin?,live_socket?,live_pid?,profile_flag?,owners_dir,job_timeout_ms,deadline_at,warm_ms?,env_digest?}`. Routes are `rpc|new|live`. `omp_bin` is present only for RPC/new; live jobs freeze `live_socket` and `live_pid`. `owners_dir` and the applicable paths are frozen at send. `warm_ms` (v0.2 W4) is present only when the effective warm duration (`send --warm`/`GLEN_WARM`) is above 0 on the `rpc` or `new` route; `env_digest` is present on every `rpc` and `new` job regardless, never on a live job (§A21). Optional disk fields are omitted when absent; readers tolerate unknown fields.
- **`status.json`:** `{v,status,updated_at,worker_pid?,worker_start?,omp_pid?,rpc_protocol?,request_id?,actual_session_id?,actual_session_file?,delivered_as?,waited_ms?,waiting_for_lock?,omp_reused?,forked?:{from,to},error?:{code,message,hint?,details?},warnings:[]}`. `omp_reused` (v0.2 W4) is true only for a job that ran on an omp process a warm worker kept from an earlier job (§A21); it is omitted, not `false`, on disk when the job never adopted one, and every job view still reports it as a present boolean.
- **`result.json`:** `{v,prompt_status?,agent_invoked,assistant_text?,replies:[],command_output:[],stop_reason?,session_settled,settled_at?}`. Result is published before terminal status.
- **Queue display:** `waiting_for_lock:true` is published only after the blocking acquire encounters contention, and cleared on acquisition before omp startup or when cancellation/timeout ends the wait. `waited_ms` retains the acquired lock’s wait duration. Human observers show "queued behind another glen job" only while that marker is true, "starting omp" otherwise, and "waiting for the reply" after acceptance.
- **Statuses:** `queued → accepted → completed|aborted|failed`, and `queued|accepted → lost`. A worker checks terminal state before claiming.
- **Lost identity:** readers compare the pid and process start time (Linux `/proc/<pid>/stat` starttime; macOS `proc_pidinfo` start timestamp). A gone process, zombie or mismatched token persists `lost`. Unknown identity is not evidence of loss. With a null pid only, status older than 10 s exceeds spawn grace. A live matching worker is never marked lost. Loss detection re-reads status under the same status lock used by worker publications, preserving any newer terminal outcome. If a reader cannot persist `lost` (an unwritable job directory or status lock), it still reports `lost` (exit 7) with the warning `lost_write_failed`, writes nothing to stderr, and leaves the stored status unchanged; `jobs` reports that warning once per job.
- **Claimant rule (v0.2 W4, §A21):** a warm worker's compare-and-claim write replaces a stolen job's `worker_pid`/`worker_start` with its own, in the same write that sets `omp_reused:true`, so the job's liveness holder passes from its blocked cold `__worker` to the claimant without a gap. That blocked worker then refuses every further status write of its own, including a timeout, a forced failure or a panic, once the on-disk status names another live pid, and exits 0 with a log line and no write. The reader's loss check (`jobs::wait::observe_with`) keeps watching rather than marking a child-exited job lost while its on-disk `worker_pid` still names a different, live process; it marks it lost, as before, once that process is proven gone.
- **Unsupported platforms.** Only Linux and macOS provide process start tokens. On other Unix, or when a token cannot be read, a worker records its pid without `worker_start`; readers conservatively cannot mark that job lost, even if it later dies. The null-pid grace does not apply to a recorded pid. This limitation is unsupported-platform behavior, not a fallback to the null-pid grace.
- **Deadline:** `GLEN_JOB_TIMEOUT` is parsed at job creation (1ms–24h, default 60m); invalid/zero values warn and use 60m. The recorded absolute deadline never resets. Before a result, timeout aborts and fails with `timeout`; after a completed result but before settlement it completes with `session_settled:false` and warning `settle_timeout`.
- **Job error codes:** `no_route`, `timeout`, `cancelled`, `aborted`, `omp_error`, `omp_exited`, `omp_unavailable`, `reply_tool_rejected`, `session_moved`, `session_switched`, `not_delivered`, `rpc_error`, `protocol`, `io`, `spawn`, `lost`, `internal`. `not_delivered` (live route): the request was acknowledged but omp never consumed it — the delivery deadline passed or a queued message was removed before delivery; the job fails with exit 7 and never adopts an unrelated run.
- **Clarifications (W2 conformance, 2026-10-30):**
  - *Never-ready omp vs the job deadline.* Whichever bound fires decides the code: the job deadline (`GLEN_JOB_TIMEOUT`) → `failed` `timeout`; the 60 s ready bound with deadline time left → `failed` `omp_unavailable`.
  - *Job handle shape first.* `glen wait <arg>` validates the handle shape before any lookup: a malformed argument is exit 2 `usage` even when `GLEN_HOME` does not exist; a well-formed handle with no `GLEN_HOME` or no match is exit 3 `not_found`.
  - *Lost detection age.* "older than 10 s" is measured on `status.json`'s `updated_at` field (the authoritative clock), not the file mtime.
  - *Abort bound.* With no control on omp, the worker publishes aborted within 1 s (tests allow 0.5 s scheduling slack). An in-flight control occupies omp's serial loop; abort queues behind it and W2 escalation bounds completion at 13 s (10s ABORT_GRACE, then 1s KILL_GRACE). No new control is dispatched after stop.
  - *Worker cwd.* omp runs in the session header's `cwd` when it is an existing directory; otherwise in the `--cwd` directory when one was given; otherwise in glen's process cwd.
- **Exit mapping:** completed → 0 (11 when forked); failed `no_route` → 6; other failed/aborted/lost → 7 `job_failed` with `{status,job,error,forked}` details. A bound expiring while queued/accepted → 10 with `ok:true` and a running document; under `wait --for reply` an unseen reply also returns 10, with `woke:"reply"` (§A20). Foreground SIGINT prints that document with `interrupted:true` and exits 130; worker/omp continue. Worker SIGTERM/SIGINT/SIGHUP abort with `cancelled`.
- **Control seam (W3b):** atomically drop `jobs/<id>/control/<name>.json` = `{v:1,op,args,deadline_ms}` (Unix ms). Replies are `{v:1,ok:true,data?}` or `{v:1,ok:false,error:{code,message,details?}}` at `<name>.done.json`, then remove the request. Dotfiles/results are ignored. The polling loop is 50ms during a run; startup/lock wait defers non-abort ops until a client exists. The worker runs list_models, set_model, and set_thinking_level one at a time off that loop on its held client, with 30s list/model and 10s other budgets bounded by the job deadline. Expired requests answer timeout unrun. Compact answers busy. Pending ops at job end answer job_ended; an in-flight request is skipped until its actual result arrives after scope join, preventing duplicate application. Abort acknowledgement carries data.job_status and session_id/queued. Startup cancellation publishes terminal status/ack before joining the bounded startup thread.
- **Live job semantics:** no glen session lock and no omp child. The existing detached worker and wait/jobs lifecycle apply. Ack publishes accepted and delivered_as; reply events append jobs/replies and result in order. Every failure after send writes result before status. Settled completed/aborted/error maps completed/aborted/failed omp_error; shutdown or EOF fails omp_exited; ack mismatch fails session_moved with from/to details. Unknown events are ignored. Ack has a 10s bound (protocol/delivery_unknown), and the earlier absolute deadline is timeout. A post-ack deadline does not interrupt omp; the hint distinguishes consumed from still queued. Worker signals abort observation with cancelled and live_turn_continues. Live control abort returns unsupported_op with “stop the run with `glen abort <session>`”; other control files explain the socket route, and the job continues. Send-frame writes have ≤200ms cancellation checks and a 2s total budget; after a broken pipe, reading the peer's last line is bounded by min(1s, that budget) and the same cancellation.
- **A2A task state (introduced in v0.2 W2).** Job views gain an append-only `task_state` field that names the job's state in A2A's task-state vocabulary. glen borrows the names only: it speaks no A2A protocol, and A2A over HTTP is out of scope (§A1). `status` stays authoritative and keeps its exit mapping; `task_state` follows from `status` and `error.code`:

| glen `status` | Condition | `task_state` |
|---|---|---|
| `queued` | | `submitted` |
| `accepted` | | `working` |
| `completed` | forked too (exit 11) | `completed` |
| `aborted` | includes the worker-signal `cancelled` code | `canceled` |
| `failed` | `error.code` is `no_route` (exit 6) | `rejected` |
| `failed` | any other `error.code` | `failed` |
| `lost` | | `failed` |

- `aborted` covers a caller stop (`error.code` `cancelled`), an omp-side abort of the prompt (`aborted`, `src/rpc/worker.rs:1548-1556`, `src/live/drive.rs:147-150`) and a session switch (`session_switched`, `src/live/drive.rs:161-167`); A2A `canceled` does not say who stopped the task, and a caller that needs the cause reads `error.code`.

## §A8 Handles
- **Session handle** = the **last 7 hex digits** of the dash-free session id.
  - omp ids are uuidv7, created with `Bun.randomUUIDv7()`. The leading 48 bits are a millisecond timestamp, so sessions created minutes apart share 6–8 leading hex digits. Fixture sessions A and S share `01a0f6b`, so prefix handles would be long and would keep growing.
  - Bun keeps the final 8 bytes random. A tail handle is therefore fixed-length, independent of the other sessions (stable), and unique with probability about 1 − n²/2²⁹ (n = 5,000 → about a 5% chance of any collision).
  - On a collision, `ls` shows the shortest unique longer tail for the colliding sessions only.
  - Legacy non-uuid ids use the shortest unique prefix, at least 7 chars.
- **Job handle** = `j` + the last 7 hex of the job id. A hex id never contains `j`, so job and session handles cannot be confused. A `j…` argument where a session is expected → `usage`, with a hint to use `glen wait`.
- **Resolving `<session>` arguments:**
  1. `@latest` = the newest session (by mtime) in the bucket of the cwd, or of `--cwd`.
  2. A path (contains `/` or ends `.jsonl`) = that file.
  3. Otherwise match case-insensitively over all sessions in `sessions_dir`. Take the union of: the full id; a hex suffix of the dash-free id (at least 4 hex); an omp-style prefix of the id or file name (at least 8 chars); a session whose catalog-assigned handle (as `ls` prints it, including a 7-char legacy prefix) equals the argument. Every handle `ls` prints therefore resolves back to its session.
     - One match → resolved.
     - Several → exit 4 `ambiguous`, with the candidates in `error.details.candidates`.
     - Two files whose headers carry the same session id (a copied file) are two candidates even for a full-id match. glen never picks one silently, because omp keys the lease by id and both copies share it.
     - None → exit 3 `not_found`.
  4. Then follow continuations.
- `@new` is valid only for `glen send`.

- **Send rules:** `--steer` / `--follow-up` alias `--as` and conflict with explicit `--as` or each other. With `@new`, `--cwd` sets the new session's directory, which must exist: a `--cwd` that is not a directory is `usage` (exit 2) with `details:{reason:"missing_cwd",cwd}` and the hint `check the --cwd path`, before stdin is read or a job exists. For every existing target (handle, id, prefix or `@latest`), it scopes resolution to that project's bucket; `@latest` means that bucket's newest session. A match found only elsewhere is `not_found` with `details:{reason:"outside_cwd",cwd:<absolute DIR>}` and a hint naming its project. An explicit file path bypasses the bucket filter and is resolved against the process cwd. omp runs in an existing recorded session cwd; only a missing recorded directory falls back to `--cwd`, then to glen's process cwd (AC-1007–AC-1012, superseding AC-209's selector restriction). Message `-` reads stdin; empty, non-UTF-8 or more than 512 KiB is usage. RPC auto/follow-up sends `streamingBehavior:followUp`, steer sends `steer`; idle baseline reports `delivered_as:prompt`.
- **Install:** installed/unchanged/upgraded/reinstalled/replaced/removed/not_installed/skipped; unchanged leaves inode/mtime untouched. Marker line is `// glen-extension version=<v> protocol=1 digest=<xxh64-seed0-body-hex16>`. A newer, edited or foreign file is skipped with extension_newer/modified/foreign unless --force; uninstall also protects modified/foreign files. --dry-run reports the action without any writes. Uninstall removes only index.ts and the empty glen dir (a sibling is preserved with extension_dir_not_empty). It never creates GLEN_HOME. Human output explains the tool and uninstall command, plus restart guidance on changes. For replace/upgrade (install-extension and install-skill alike), glen publishes with an atomic exchange (`renameat2(RENAME_EXCHANGE)` on Linux, `renameatx_np(RENAME_SWAP)` on macOS), then checks that the displaced file is the one it inspected (dev, ino, xxh64 digest) before deleting it. A file another writer put there after glen's last check is swapped back and left in place, and the install reports `skipped` with `changed_during_install`; if even the swap-back cannot be verified, the displaced copy is kept and its path named in the error. On a filesystem with no atomic exchange (EINVAL, ENOTSUP/EOPNOTSUPP, ENOSYS) glen falls back to a plain rename and warns `replace_not_atomic`; only then can a replacement made in that window be overwritten. Any other swap error fails the install without falling back (AC-1017–AC-1019). glen never writes the extension file through a symlink. A symlink at the extensions dir, the glen dir or index.ts makes the file `foreign`: install-extension skips it with `unsafe_path` (even with --force) and doctor's extension row warns with the same message. A failed directory sync after publishing warns `extension_sync_failed`. Extension and skill versions compare by semver precedence (a release sorts above its pre-releases, numeric pre-release ids compare as numbers, build metadata is ignored); a version that is not `major.minor.patch` sorts below every valid one.
- **Inbox:** --session matches full id or ≥4 hex tail, case-insensitive; --peek leaves cursors untouched; --all includes read records. With --cwd, filter by the catalog and registry project bucket; session handles and prefixes use the same matcher as show, and --session intersects the project scope. If only foreign stems match, non-follow output warns outside_cwd. Unclassified replies stay unread; without --cwd, the inbox aggregates all projects. While a stem is unclassified, follow rescans the catalog at most once every 3 s, including for sessions created after startup, so a new session's first reply can take a few seconds to appear. Sort by parsed at, then stem/file offset; malformed timestamps sort last. Missing home/inbox is empty and lazy. -f always emits NDJSON, polls every 250ms including new files, and commits after successful message output; SIGINT writes end and exits 130. --wait (v0.2 W2) conflicts with -f and --all, takes the same scope, and checks every 250ms until one record is unread (exit 0, the normal document) or --timeout passes (exit 10, `messages:[]` and a `next` command; nothing marked); --timeout requires --wait (§A20).
- **Global flags:** `--json`, `--human` (mutually exclusive), `--color auto|always|never`, `--profile NAME`, `-h`, `-V`.
- **Defaults and aliases:** `--color` defaults to `auto`; `--profile` overrides `OMP_PROFILE` and `PI_PROFILE`. `ls` and `jobs` use `-n/--limit` (default 20); `tail` uses `-n/--lines` (default 10). `tail` and `inbox` accept `-f/--follow`. `show --tools` defaults to `collapsed`; `send --as` defaults to `auto`; `send --wait`, `wait --timeout` and `inbox --timeout` (with `--wait`) default to `90s`. `wait --for` takes `reply`, its only value; `wait --after <reply-id>` requires `--for`. `send --warm` defaults to off (0, or an absent `GLEN_WARM`); `release --timeout` defaults to `10s` (v0.2 W4). `-h/--help` and `-V/--version` are available on every command. Unfinished commands remain hidden and return `not_implemented` (exit 8).
- **Durations:** `<n>ms|s|m|h` or bare seconds, at most 24h. `--wait 0` equals `--no-wait`. `ls --since` accepts `<n>s|m|h|d|w` or bare seconds, at most 3650 days.
- **Internal:** `glen __worker <job-id>` (W2), always hidden. `glen __acp <session|@new> <message> [--permission allow|deny]` (v0.2 W3), a hidden spike, not a public contract (§A23). `glen mcp --channel` (v0.2 W5), a permanently hidden flag on the now-visible `mcp` command: an unsupported, protocol-tested-only notifier (§A22).
- **Considered and rejected:**
  - a `glen reply` CLI: the reply path is the `glen_reply` tool, and an omp Bash call has no job context;
  - a separate `glen steer` verb: folded into `send --as`;
  - a `--new` flag: an optional first positional is ambiguous, so it became `@new`;
  - an MCP server: not needed for v0.1.0; ships in v0.2 W5 as an exec-self layer over the CLI, not a second implementation (§A22).

**Excluded controls:** auto-compaction, steering/follow-up/interrupt queue modes and auto-retry are session-only RPC overrides with persist=false and have no equivalent extension setter. Cycle model/thinking duplicates explicit selection. Service tier/fast mode is provider-specific and deferred. Clearing queued messages has no extension equivalent. Thinking auto/inherit is a documented v0.1.0 gap. Cancelling queued glen jobs remains outside this wave. W4's already-visible install-skill remains available; watch is unchanged.

## §A10 Output contract
`docs/json.md` is the normative per-command contract; this section keeps the rules.
- **Modes.** `--json` → JSON; `--human` → human; otherwise human when stdout is a TTY and JSON when it is not. Raw commands (`completions`) print raw unless `--json` is given. `--help` and `--version` are always text. Without `--json`, a raw command renders every error — usage, env (e.g. a relative `GLEN_HOME`, AC-020) and internal alike — as human text on stderr with an empty stdout, so stdout is never anything but the script itself (e.g. `glen completions zsh >> ~/.zshrc` can never append an envelope); with `--json` the error is the usual JSON envelope on stdout.
- **Streams.** stdout carries only the result. stderr carries diagnostics, warnings (human mode) and spinners. In JSON mode stderr stays empty except for panics.
- **Envelope** (`v` = contract version 1; fields are append-only; keys are snake_case; timestamps are RFC 3339 UTC; durations are `*_ms` integers; JSON paths are absolute):

| Document | JSON contract |
|---|---|
| Success | `{"v":1,"ok":true,"data":{…},"warnings":[{"code","message"}]?}` |
| Error | `{"v":1,"ok":false,"error":{"code","message","hint"?,"details"?},"warnings"?}` |
| Spilled | `{"v":1,"ok":true,"spilled":{"path","bytes","format":"json"|"text"}}` |

  - Pretty-printed on a TTY, compact otherwise.
  - `ok:true` holds for exits 0, 10, 11 and observer interruption 130.
- **Doctor data:** `data.glen` contains `version`, `home` and `home_exists`; `data.omp` contains `bin` (path or null), `version` (the normalized `omp --version` text, or null when it cannot be parsed or omp cannot run), `tested_version` (`18.14.0`), `supported` (`{min,max_tested}` from `src/omp/compat.json`) `capabilities` (null unless `--probe` ran, else `{protocol,host_tools,event_filter}`, §A19) and `approval` (`{mode,source}`, omp's `tools.approvalMode` for the profile, §A13). `data.paths` contains the §A12 resolved paths, `profile` (name or null), `agent_dir_source` (`default|profile|env`) and `sessions_dir_source` (`agent_dir|xdg`). `data.checks` is an ordered array of `{name,status,value,detail}`, with status `ok|warn|fail|info`. `value` is the raw absolute path or check value; `detail` is the reason for the status, or an empty string when there is none. The checks are `omp_binary`, `omp_version`, `omp_capabilities`, `profile`, `agent_dir`, `sessions_dir`, `glen_home`, `extension`, `live_endpoints`, `warm_workers`, `omp_env_files`, `skill_claude`, `skill_codex`, `sandbox`, `omp_approval`. `data.extension={path,state,version,current}` describes current/not_installed/outdated/newer/different_home/modified/foreign. live_endpoints reports N live, M stale by pid, warning on unreadable registries or socket path limits. `warm_workers` (v0.2 W4, §A21) reports `<w> warm, <s> stale, <d> dead` from `run/warm` alone, never a probe: `info` when nothing is stale or unreadable, else `warn` naming the stale handle(s) and `glen release <handle> --force`; it never fails doctor. `data.skills` contains claude/codex `{path,state,version,current,project}`, with project null or `{path,state,version}`. W4 rows are advisory, never fail. `omp_approval` (audit S-01, §A13) is `ok` for a non-yolo mode and `warn` for `yolo` (with warning `omp_approval_yolo`) or `unknown` (with warning `omp_approval_unknown`); it never fails doctor. The version never fails doctor on its own (v0.2 W1): above `max_tested` it is `warn` with warning `omp_version_untested`, below `min` `warn` with warning `omp_version_unsupported`, and output that cannot be parsed is `warn` with value `unprobed` and warning `omp_version_untested`. `omp_capabilities` is `info` `not probed` without `--probe`, `info` `skipped` when the binary is missing or `--version` failed, and otherwise `fail` only when `host_tools` is proven missing (exit 5), `ok` when all three capabilities are known and ok, `warn` otherwise. A failed doctor returns `omp_unavailable`, with the same data under `error.details.report`, and its human table before the error line. Missing directories are reported without creating them.
- **Install-skill:** `{version,dry_run,scope,targets:[{agent,path,action,state,installed_version}]}`; state/version describe the pre-run file (null version when absent). Both agents are selected by default; flags select one or both. User targets: `$CLAUDE_CONFIG_DIR/skills/glen/SKILL.md` (nonempty, relative to cwd), else `~/.claude/skills/glen/SKILL.md`; Codex `~/.agents/skills/glen/SKILL.md`. Project targets are cwd `.claude/skills/glen/SKILL.md` and `.agents/skills/glen/SKILL.md`. Directories are 0755 before umask; files atomic 0644 before umask; glen never chmods past the umask. No GLEN_HOME is created. Inspection of all selected targets precedes writing. Destination and ancestor identities (dev/ino and file digest) are revalidated before rename/unlink; a concurrent change skips with `changed_during_install`, including under --force. Identical files stay untouched; intact older/same-version other builds upgrade, newer/modified/foreign skip unless --force. Directory symlinks below the scope root always skip; links at/above it are followed. Uninstall removes only the file and empty glen directory. Dry-run changes nothing. IO errors include `details.done` and collected warnings.
- **W4 cycle 1 clarifications:** `omp_env_files.value` is an array of absolute paths (§A10 wins over AC-409 tilde wording). A stale digest means `modified` even for an older version; user edits require --force. Another agent or foreign marker has `installed_version: null`. Uninstall skips modified/foreign files with the same warning code as install. Project installs need no HOME; user installs with HOME unset return `invalid_env`. Only non-empty `CODEX_SANDBOX` marks a Codex sandbox (empty is unset); `CODEX_SANDBOX_NETWORK_DISABLED=1` alone permits send and maps actual permission failures to exit 6 `sandboxed`. The doctor sandbox row for that case is "network disabled by the host; escalated commands still work" everywhere except Linux, where any marker hides omp's lease — see the W10 clarification in §A13 for the Linux rule and its own doctor row.
- **W4 cycle 2 clarification:** warning code `changed_during_install` means a destination or ancestor changed after inspection and was skipped, even with --force. A stale digest means `modified` for older, same and newer versions; user edits always win and skip without --force. Foreign/other-agent markers have both `installed_version: null` and doctor `skills.<agent>.version: null`. With either Codex marker (non-empty CODEX_SANDBOX or CODEX_SANDBOX_NETWORK_DISABLED=1), permission/read-only failures writing GLEN_HOME, including spill and job writes, map to exit 6 `no_route` with `details.reason:"sandboxed"`; without a marker they remain `io`.
- **W1 reader documents.** `ls` returns `{scope:{all,cwd,bucket},sessions_dir,total,total_all,sessions:[]}`. Scope cwd/bucket are null with `--all`; total is after filtering but before limiting. Each session has `handle,id,path,bucket,cwd,title,first_message,created_at,updated_at,age_ms,size_bytes,model,last_turn,state,state_source,state_detail,continuation_of,parent_session`; nullable fields remain present as null. Future mtimes saturate age_ms at zero (human: `just now`).
  - `show` and document `tail` return `{session,continued_from,leaf_id,skipped_lines,items:[]}`. `show --raw` replaces items with active-branch `entries:[]`, including unknown entry kinds. `tail -n 0` returns an empty items array.
- **W2 send/wait documents:** completed data is `{status:"completed",job,session:{id,handle,path},assistant_text,replies,command_output,stop_reason,session_settled,delivered_as,forked}`. `forked` is null or `{from,to,to_handle}`. RPC `session` identifies the resolved target after following continuations (the session the job was sent to, e.g. C when B continued in C); the new route uses the actual session identity. Nullable output fields remain present.
  - Running/interrupted data is `{status:"running",job,session,next:"glen wait <handle>",interrupted}`; workers keep running after exits 10/130. Under `wait --for reply` it adds `replies` (the unseen replies) and `woke:"reply"` on a reply wake, which a bound expiry omits; `next` is `glen wait <handle> --for reply` plus `--after <last reply id>` (§A20).
  - Job view: `{id,handle,status,task_state,route,deliver_as,delivered_as,session_id,session_handle,actual_session_id,created_at,updated_at,elapsed_ms,omp_reused}`. `task_state` (v0.2 W2) is derived from `status` and `error.code` as in §A7's table. `omp_reused` (v0.2 W4) is true only for a job that ran on an omp process a warm worker kept from an earlier job (§A21).
  - **W4 documents.** `glen release` returns `{total,workers:[{session:{id,handle},job,pid,state:"idle"\|"busy"\|"stale"\|"dead",outcome:"released"\|"cooling"\|"forced"\|"cleaned"}]}`; no target and no `--all` match is exit 3 `not_found` (`not_warm`); a worker that does not release within `--timeout` without `--force` is exit 7 `control_failed` (`release_timeout`, with the pending `workers`) (§A21).

Rows add `text_preview` (first line, controls dropped, up to 80 characters), `error` and `forked`. `-n 0` means all; active filtering runs after lost detection. `--session` matches original or actual id, or at least 4 hex suffix digits. Missing GLEN_HOME yields an empty list without creating it.

Human single-line fields such as titles, previews and tool summaries first collapse whitespace runs (including newlines and tabs) to one space, then sanitize. A literal ESC followed by `[31m` is displayed literally as `\x1b[31m`. JSON fields retain the raw value, including controls and whitespace, with serde escaping on the wire; on top of that, glen escapes DEL, C1 controls (U+007F–U+009F) and bidi controls (U+061C, U+200E–F, U+202A–E, U+2066–9) as `\uXXXX` in documents and NDJSON, so a terminal showing raw JSON never interprets them and parsers decode the same value. Documented preview/result length limits still apply. Spinner messages are sanitized too.
- **Write failures (AC-1001/AC-1002, amending AC-029).** When a stdout write or flush fails with EPIPE (the reader closed the pipe), glen writes nothing more to stdout or stderr and keeps the outcome's own exit code: 0 for success, the error's code for a failure envelope, or 10, 11 or 130 for a running, forked or interrupted outcome. This applies to every command and mode, including JSON, human, raw and clap help/version/usage. Any other stdout failure exits 1, without a panic or a second JSON document. A failed stderr write also exits 1; clap usage successfully written to stderr keeps exit 2 regardless of stdout.
- **Lazy state.** `--help`, `--version`, `doctor` and path resolution never create `GLEN_HOME`. Directories are created on first write (spill in W0; jobs, inbox and live endpoints later).
- **v0.2 W5 documents.** `glen mcp` (§A22) prints no JSON envelope of its own; each tool's result is the CLI's own document for the command it wraps, with `isError` mirroring `ok`. Two new `details.reason` values appear under this contract: `mcp_arguments` (usage, the arguments did not fit the tool's schema) and `mcp_exec` (internal, glen could not be run to an envelope).

### W3b control documents
`docs/json.md` defines the full five documents. Each carries session `{id,handle,path}` (path null before persistence) and route. Model returns model/previous/changed/thinking_level/thinking_levels/busy/scope/forked; thinking returns requested/previous/changed/model/available/busy/scope/forked; compact returns compacted/tokens_before/tokens_after/forked; abort returns was/aborted/idle_after/queued/queued_jobs (job route adds job/job_status). Forked is null or `{from,to,to_handle}`. Endpoint-only changes warn not_yet_persisted. ls still reports the last answering model, which may differ from models current until the next turn.

Human forms name the session and route: “nothing to abort”, “stopped the running turn”, provider/id with thinking level, or compacted token counts. Models renders a COLUMNS-bounded MODEL / NAME / CONTEXT / THINKING table, truncating NAME first and marking current. omp-sourced strings are sanitized only for presentation.

control_failed exits 7: no_auth (log into provider), busy (abort first or wait), omp_error (omp's message), timeout, session_moved, job_ended, protocol, outcome_unknown (the change may have been applied; check `glen models <h>` before retrying). invalid_level is usage/2; model_not_found is not_found/3; model ambiguity is 4. Exact provider/id wins over case-insensitive pair/bare-id resolution. The extension supplies all available models; RPC may apply its enabled-model filter. Same-version installed extensions with an intact digest, matching baked GLEN_HOME and older body are outdated (“older build”), upgraded by install-extension and warned by doctor; a different home remains reinstalled.

### W3 conformance clarifications

- AC-321's TUI notice is once per failing `session_start`, so a later start gets its own notice.

- `inbox --session` rejects hex suffixes shorter than four digits with exit 2, `usage`, in both normal and follow mode. Full session ids remain accepted.
- Adjacent queued user messages consumed in the same run with no intervening assistant output share a batch reply span. ## §A11 Exit codes

A closed stdout pipe (EPIPE on write or flush) preserves the outcome's code below, including failure codes such as 2 (`usage`), 3 (`not_found`), 5 (`omp_unavailable`) and 6 (`no_route`), and statuses 10, 11 and 130. It does not turn failures into success: glen stops without further stdout or stderr output. Other stdout failures and failed stderr writes exit 1. Clap usage successfully written to stderr keeps exit 2 regardless of stdout (AC-1001/AC-1002).

| Exit | `error.code` / status | Meaning |
|---|---|---|
| 0 | — | success (`ok:true`) |
| 1 | `internal`, `io` | unexpected failure |
| 2 | `usage`, `invalid_env` | bad flags or arguments; bad env value (`OMP_PROFILE`, `PI_PROFILE`, `GLEN_HOME`, missing `HOME`) |
| 3 | `not_found` | session, job or handle not found |
| 4 | `ambiguous` | handle matches several; candidates in `details` |
| 5 | `omp_unavailable` | omp missing or unrunnable (failed or timed-out --version), or doctor --probe proves a required capability missing; an unparseable version is a warning (§A19) |
| 6 | `no_route` (foreground or worker-side refusal) | live owner without a glen endpoint, probe unknown, or a sandbox that cannot reach omp (`details.reason:"sandboxed"`); refusing to fork |
| 7 | `job_failed`, `control_failed` | failed/aborted/lost job, or a control failure with details.reason (including `release_timeout`, v0.2 W4 §A21) |
| 8 | `not_implemented` | subcommand declared but not in this build |
| 10 | (ok) `running` | wait bound elapsed; job continues; use `glen wait <job>`. With `--for reply`, `data.woke:"reply"` marks new replies and its absence a bound expiry (§A20); `inbox --wait` uses 10 for its bound |
| 11 | (ok) `forked` | omp moved the session to a continuation; use the new handle |
| 101 | — | watch panic; terminal teardown runs before the panic report |
| 129 | — | watch received SIGHUP, or a control received a second SIGHUP; `glen mcp` also exits 129 on SIGHUP after ending every call still running |
| 130 | — | interrupted (SIGINT), including watch; send/wait print a running document with `interrupted:true`; a detached job keeps running. Controls also exit 130 on SIGTERM or SIGHUP, with the interrupted document. `glen mcp` exits 130 on SIGINT the same way. `doctor --probe` has no interrupted document: a SIGINT, SIGTERM or SIGHUP during the probe tears the omp group down first, then ends glen through SIGINT's own default disposition (130 in a shell) on all three signals (§A19) |
| 143 | — | watch received SIGTERM, or a control received a second SIGTERM; `glen mcp` also exits 143 on SIGTERM after ending every call still running |

## §A12 omp path resolution (port of `packages/utils/src/dirs.ts` @ v18.14.0)
1. **home** = `$HOME` if non-empty, else the passwd entry. If neither exists → `invalid_env`.
2. **Base config root** = home joined with `PI_CONFIG_DIR` (if non-empty, else `.omp`), using Node `path.join` semantics: an absolute value lands *under* home, and `..` is normalised lexically. The base is profile-independent.
3. **Profile** = `--profile`, else `OMP_PROFILE` if set (even an empty value selects default), else `PI_PROFILE`.
   - Trimmed. Empty or `default` → the default profile.
   - Valid: `^[a-z0-9][a-z0-9._-]{0,63}$`, not `.` or `..`, not ending in `.`, not a Windows reserved basename.
   - Invalid flag → `usage`; invalid env → `invalid_env`.
4. **Config root** = base, or `base/profiles/<p>`.
5. **Agent dir:**
   - named profile → `config_root/agent`, and `PI_CODING_AGENT_DIR` is ignored;
   - default profile → `PI_CODING_AGENT_DIR` (non-empty, resolved against the cwd), unless it equals `base/profiles/<PI_PROFILE>/agent` (a profile-derived value, ignored);
   - otherwise `config_root/agent`.
6. **XDG** (Linux and macOS), only when the agent dir is the profile's default:
   - `XDG_DATA_HOME` non-empty and `<XDG_DATA_HOME>/omp` exists (named profile: `<XDG_DATA_HOME>/omp/profiles/<p>` exists) → sessions = `<that>/sessions` (flattened, no `agent/`);
   - otherwise `agent_dir/sessions`.
7. **Session owners** = `<XDG_STATE_HOME>/omp/run/session-owners` if `XDG_STATE_HOME` is non-empty and `<XDG_STATE_HOME>/omp` exists, else `base/run/session-owners`. This is shared across profiles and ignores the agent-dir override.
8. **Extensions** = `agent_dir/extensions` (no XDG redirect).
9. **Known gap.** omp fills *unset* `PI_CODING_AGENT_DIR`/`XDG_*_HOME` from `.env` files (cwd `.env`, `<agent_dir>/.env`, `<config_root>/.env`, `~/.env`; `utils/src/env.ts:289-316`). glen reads only its own environment. Doctor’s `omp_env_files` warns when these files assign PI_CODING_AGENT_DIR, OMP_CODING_AGENT_DIR, XDG_DATA_HOME or XDG_STATE_HOME while the corresponding glen variable is unset/empty. Unreadable files are skipped; OMP_CODING_AGENT_DIR maps to PI_CODING_AGENT_DIR.

- **W4 cycle 1 path clarification:** every §A12 path variable, including `CLAUDE_CONFIG_DIR`, treats whitespace-only values as unset. `.env` detection checks PI_CODING_AGENT_DIR and its OMP_CODING_AGENT_DIR alias, plus XDG_DATA_HOME and XDG_STATE_HOME.

- **W4 cycle 2 clarification:** the OMP_CODING_AGENT_DIR alias also applies to glen's own process environment: when PI_CODING_AGENT_DIR is unset/empty, a non-empty OMP_CODING_AGENT_DIR counts as set for path resolution and suppresses dotenv warnings for either spelling.

- **Environment handling difference.** glen drops non-UTF-8 environment keys/values and treats whitespace-only path values as unset; omp uses JavaScript strings and treats whitespace-only values as set. Profile names are still trimmed. `NO_COLOR` and `CLICOLOR_FORCE` use literal values as specified in §A10.

- **omp executable:** `GLEN_OMP_BIN` (non-empty) accepts an absolute file path or a bare executable name searched on PATH; otherwise glen searches PATH for executable `omp`. `doctor` runs `--version` with a 10 s deadline and normalizes the first stdout line, trimmed: `[omp/][v]MAJOR.MINOR.PATCH[-PRE][+BUILD]`, `PRE` and `BUILD` limited to `[0-9A-Za-z.-]` (v0.2 W1, §A19). Failure (spawn error, non-zero exit, non-UTF-8) or timeout stays `omp_unavailable`; output that cannot be parsed, an empty line included, is a warning (`unprobed`).

## §A14 Security and privacy
- Local only; no network.
- GLEN_HOME is 0700. The socket's only protection is filesystem permissions (a same-user boundary).
- Sandboxed writers (owner decision, 2026-11-08): a sandboxed or write-only agent given the real GLEN_HOME for live delivery (§A13) is in the threat model, scoped. It may add messages and jobs; it must never take over an existing session or process. So a warm worker must not adopt a job it did not authorize (S-03), a `send` must not reach a socket that is not the registry's own endpoint (S-18), and `release --force` must not signal a process it cannot identify (S-09). Such a writer runs as the owner's uid and can read GLEN_HOME (sandboxes restrict writes, not reads), so no secret stored there can tell a legitimate glen from it. glen relies on kernel facts about other processes instead (`src/proc_ident.rs`): a socket's peer credentials, a process's confinement, its executable image, argv and ancestry.
- **Confinement ordering.** glen never hands work to, or accepts work from, a peer more confined than itself, judged on kernel facts the peer cannot undo. Linux ranks the two processes: the peer is no more confined when it sets `NoNewPrivs` only if glen does, its `Seccomp` mode in `/proc/<pid>/status` is at most glen's, and it shares glen's user, pid and mount namespaces; a peer in other namespaces passes only when it carries no confinement at all and glen does (glen in the sandbox, the peer on the host). The `ns` links are ptrace-gated, so from inside a bwrap user namespace the host's processes hide them (EACCES): when glen runs in a user namespace of its own (`uid_map` not the identity map) and the peer's links are refused with EACCES or EPERM, the peer is outside glen's namespaces and is ranked on `NoNewPrivs` and `Seccomp` alone, which `status` still shows. Anywhere else an unreadable peer is unknown and refused (from the initial user namespace only a process that made itself non-dumpable hides them). So a glen in a container or toolbox still refuses a peer that confined itself further. glen's own facts come from `/proc/self`. macOS cannot rank: a Sandbox.kext profile (`sandbox-exec`, seatbelt, App Sandbox) is read through libSystem's private `sandbox_check` / `sandbox_check_by_audit_token`, looked up at run time (an error or a missing symbol is unknown), and a confined glen allows any peer: it is an add-only principal already. An unknown answer is refused (availability only). A peer pid the kernel cannot map (0: glen in a child pid namespace, the peer outside it) is accepted only when glen is confined.
- **S-18 (implemented).** A live registry's `socket` must be exactly `run/live/<pid>.sock` (its directory compared by real path), and, once bound, a socket owned by this user with no group or other bits. Every connection (`hello`, `state`, `send` and the controls) reads the kernel peer before writing a byte: it must be the registry's pid, run as this user and pass confinement ordering, and `hello` must report the same pid. Each request opens a new connection, so a socket swapped after `hello` is caught at `send`. The kernel records the listener's pid at `listen()`, so a confined listener could fork a child that keeps the socket and exit, and its pid number could then name an unconfined successor. Confinement is therefore judged only for the process generation holding the listener. Linux: a `SO_PEERPIDFD` pidfd (6.5+) must still name the pid (`/proc/self/fdinfo`, `Pid:`; −1 once exited) and the pid must be a thread-group leader, before and after its confinement is read; on an older kernel, or when no pidfd can be made because the listener exited, `/proc/<pid>/fd` must hold the one listening socket bound to that path in `/proc/net/unix`, before and after. macOS: the `LOCAL_PEERTOKEN` audit token must name the pid (it fails once the listener has exited, but after pid reuse it names the successor), the pid must hold a listening socket bound to that path (`PROC_PIDLISTFDS`, `PROC_PIDFDSOCKETINFO`), and the confinement is judged by token, which answers "sandboxed" for a token whose process is gone. A refusal is exit 6 `no_route`, `details.reason:"untrusted_endpoint"`; `ls` and `show` show the session's state as `unknown` and lend it no cwd or title; no registry or socket is deleted, except a dead pid's registry, cleaned as in §A4.
- **S-09 (implemented).** `release --force` signals a worker only after proving, besides its pid and start token, that it runs this glen executable as `__worker <origin_job_id>` (a registry field: the worker's argv job, which `job_id` leaves on adoption), and the omp group only after proving omp's parent is that worker and omp leads its own group. The executable is compared by the mapped file, never by path: Linux `stat` through `/proc/<pid>/exe` and `/proc/self/exe` (device and inode, even for a deleted file); macOS the device and inode of each process's first file-backed region (`PROC_PIDREGIONPATHINFO`), falling back to the canonical `proc_pidpath` when that cannot be read. So `--force` cannot end a worker started by a glen binary since replaced (plain `release` can). Both proofs come before the first signal. Then the proven worker is stopped (SIGSTOP), so it cannot reap omp and omp's pid, with its group id, stays pinned (a zombie at worst). A SIGSTOP sent is not a worker stopped, so it must be seen stopped (Linux `/proc/<pid>/stat` state `T`, macOS `pbi_status == SSTOP`) within 200 ms, or it is resumed and nothing more is signalled (`unverified_process`). Then omp is proven again and its group killed, and the worker is killed. A worker stopped for a kill whose second proof fails is resumed. On Linux the worker and omp are each pinned by a pidfd opened before their proofs, and every worker signal goes through the worker's; a process with no pidfd is never signalled. omp's group is signalled through omp's pidfd with `PIDFD_SIGNAL_PROCESS_GROUP` (Linux 6.9+), which reaches omp's own group or none. On older kernels (`EINVAL`) and on macOS it is signalled by number, right after checking that omp has not exited (its pidfd does not poll readable; an exited omp's group number is never signalled) and that the worker is still stopped (so omp cannot have been reaped and its number reused). On macOS the worker is proven again immediately before each numeric signal (a window of microseconds). A failed proof is `release_timeout` with the row's `reason:"unverified_process"` and the registry kept; a registry without `origin_job_id` is never force-killed.
- S-03 (a warm worker adopting a job written by file alone) is planned (hardening wave H2). Pid-namespace liveness on Linux (S-04) is availability only.
- Residuals: on macOS a confined glen sends to any same-user endpoint, including another sandbox's (unranked); on Linux two different sandboxes with equal no_new_privs and seccomp mode in the same namespaces are not told apart (seccomp filters are not compared); a forged, correctly named warm registry can still make `--force` kill a real glen worker of another session (no escalation: the `.release` request and job `control/` files give the writer that power already); a writer can cool warm workers and delete sockets (availability); an owner whose omp TUI itself runs confined (Flatpak, a sandboxed terminal app) loses live delivery from an unconfined glen, with no opt-out; `inbox` and `watch` scope endpoint-only sessions by registry and confinement without connecting, so a registry naming an unconfined live process can lend them a cwd or title (display only; `ls` and `show` verify the endpoint). The socket-ownership proof matches a listener by its bound name, so it is beaten only when a legitimate glen endpoint reuses the departed listener's exact pid and the writer then renames its kept socket file over that endpoint's (Linux refuses two listeners bound to one name; macOS checks only that the pid holds one). On macOS `--force` signals the worker by number right after its re-proof. On macOS and on Linux before 6.9, omp's group is signalled by number: in the microseconds between the checks above and `kill(-pgid)`, a same-uid attacker that owns the proven worker (it can SIGCONT a process of its own uid) could resume it, have it reap omp, and have the pgid number land on a freshly created group leader; the impact is one signal to one unrelated same-uid process group (availability, no takeover). A 0600 adoption secret was rejected because the writer can read GLEN_HOME.
- GLEN_HOME and its runtime subdirectories must be owned by the current user, must not be symlinks, and must have no group or other write bit. glen and the extension refuse them otherwise (§A6 Trust) rather than chmod them.
- The extension runs unsandboxed inside omp, like every omp extension. glen ships its source in the repo and installs it only on explicit `install-extension`.
- Message text is stored only under GLEN_HOME.
- glen never writes omp session files.

## §A19 omp compatibility
Owner: **v0.2 W1** (ADR `0773c35d`, plan `.claude/plans/v020-wave-1-omp-compat.md`). glen supports a declared, tested omp range instead of exactly one version, checks omp's RPC capabilities on request, and runs its omp surface contract nightly against the latest omp.
- **The range.** `src/omp/compat.json` holds `min`, `max_tested` and `tested`, one key per line; it is the single source, read by Rust and the nightly directly, and by the site from the release PR on (the site's v0.2 copy, held in commit `39aff85` until that PR, imports the file instead of hardcoding the tested version). `omp::TESTED_OMP_VERSION` derives from `tested`. `omp-rpc` stays pinned to git tag `v18.14.0`, because Cargo cannot take a range of git tags, so the range is a declared, tested policy; a unit test fails when `tested` and the tag differ. At W1 `min` = `max_tested` = 18.14.0 (default 6). Only W6 raises `max_tested`, and only after the dispatched nightly passes on a newer omp: the `omp-latest` run 41634564429 on `main` passed against omp 18.16.0 (AC-v2-603), so the v0.2.0 release PR sets `max_tested` = 18.16.0, with `min` and `tested` still 18.14.0, the `omp-rpc` pin.
- **Normalization.** `src/version.rs` holds glen's own semver precedence (no `semver` crate): build metadata is ignored and a release sorts above its pre-releases. `parse_omp_line` takes the first stdout line of `omp --version`, trimmed, strips an optional `omp/` and then `v`, and accepts `MAJOR.MINOR.PATCH[-PRE][+BUILD]` with `PRE` and `BUILD` limited to `[0-9A-Za-z.-]`; the normalized text keeps the pre-release and build metadata. Anything else, an empty line included, is unparseable, and the raw line is never echoed beyond 64 sanitized characters in a warning message.
- **Classification and doctor rows.** Below `min` is unsupported (a pre-release of `min` included), above `max_tested` untested, otherwise supported. The `omp_version` row is `ok` with the normalized text; `warn` with detail `untested` and warning `omp_version_untested`; `warn` with detail `unsupported` and warning `omp_version_unsupported`; or, unparseable, `warn` with value `unprobed`, detail `cannot parse omp --version output` and warning `omp_version_untested`. Doctor never fails on the version alone. An `omp --version` that cannot run (spawn error, non-zero exit, timeout, non-UTF-8) stays `fail`, exit 5 `omp_unavailable`, because no version exists to judge. This supersedes W0's AC-016 for unparseable output (§A11, §A12). `data.omp` is `{bin,version,tested_version,supported:{min,max_tested},capabilities}`; the human footer reads `tested against omp <tested> · supported <min> to <max_tested> · profile <p>`.
- **The probe.** `glen doctor --probe` (`src/ctl/probe.rs`) starts `omp --mode rpc --no-ui --no-session --no-extensions --no-skills --no-rules` (plus `--profile` when given) with `GLEN_MANAGED=1` in a private, empty 0700 scratch directory (not glen's own cwd), in its own process group (v0.2 W6, security audit S-02): this keeps a throwaway probe from loading whatever extensions, skills or rules the caller's own directory happens to carry. One 30 s budget (`ctl::probe::BUDGET`) covers startup and every call: the ready wait and each call's timeout are clamped to the time left, never the 60 s ready or 10 s call defaults. It records the negotiated protocol, registers the real `glen_reply` definition (`set_host_tools`) and the worker's event allowlist (`set_event_filter`), and sends nothing else: no prompt, steer, follow-up, abort, model change or compaction. It takes no lock or lease and never creates `GLEN_HOME` or a session file. A worker thread publishes each stage under a lock that discards a stage arriving at or after the deadline, so at the deadline the main thread returns what was learned before it, with the detail `probe exceeded the <budget> budget during <stage>` (`startup`, `set_host_tools`, `set_event_filter` or `close`), and kills the group; a clamped call that times out at the deadline counts as the deadline. On the normal path the worker closes the client first, so omp exits on stdin EOF within the 1 s grace before any signal. The result is final at the budget; teardown after it is bounded (1 s after SIGTERM, 1 s after SIGKILL, 1 s for the stderr reader). omp's own process group never sees a terminal's Ctrl-C, so a SIGINT, SIGTERM or SIGHUP to glen during the probe tears the group down first and then ends glen through SIGINT's default disposition (130 in a shell): doctor has no interrupted document (§A11). SIGTERM and SIGHUP share SIGINT's flag, as in controls, so they too end `doctor --probe` through SIGINT's default disposition: a supervisor that sent SIGTERM observes SIGINT, not 143. `--version` before it keeps its own 10 s deadline.
- **Capabilities.** `{protocol: 1|2|null, host_tools, event_filter}`, each capability `ok`, `missing` or `unknown`. A rejected command (`success:false`), or a tool list without `glen_reply`, proves a capability `missing`; a timeout, closed stream, I/O, protocol or decode error proves nothing (`unknown`). `host_tools` is the only required capability, because the worker fails a job with `reply_tool_rejected` without `glen_reply` but treats a rejected filter as the warning `event_filter_rejected`. The `omp_capabilities` row (index 2, after `omp_version`) is `info` `not probed` without `--probe`, `info` `skipped` when the binary is missing or `--version` failed, and otherwise `protocol=<p> host_tools=<c> event_filter=<c>`: `fail` when `host_tools` is `missing` (exit 5 `omp_unavailable`, hint `omp lacks a capability glen needs: see the omp_capabilities row`), `ok` when all three are known and ok, `warn` otherwise. An omp that exits before `ready` is `warn`, all `unknown`, with its last stderr line in the detail.
- **Bare omp exits before ready.** Verified on 18.14.0 with a scratch HOME: `omp --mode rpc --no-ui --no-session` with no selectable model writes "No default model selected …" to stderr and exits 1 before `ready` (`main.ts:2740-2753`), so a bare probe is `warn`, never `fail`. The provider-free recipe is a loopback stub provider in the scratch HOME's `.omp/agent/models.yml` (`tests/fixtures/omp-surface/models.yml`: `baseUrl: http://127.0.0.1:9/v1`, `auth: none`, one model): omp then sends `ready` with `supportedProtocolVersions:[1,2]` and answers every surface call without contacting a provider. No credential or placeholder key is ever used.
- **Protocol in job status.** Every RPC-route job's `status.json` gains `rpc_protocol: 1|2`, written right after the omp client starts (§A7); it is not part of the job view in `docs/json.md`. A control served by an owning job's worker is covered by that job's record. An unowned RPC control runs on a foreground omp with no status file, so it records nothing, and `doctor --probe` reports the negotiated protocol instead. Missing host-tool support keeps `reply_tool_rejected`.
- **Surface contract and source facts.** `tests/omp_surface.rs` asserts once what glen needs from omp's CLI and RPC: `--version` parses, `--help` lists 10 flags (`--mode`, `--no-ui`, `--no-session`, `--resume`, `--profile`, `--thinking`, `--extension`, `--no-extensions`, `--no-skills` and `--no-rules`), RPC reaches `ready`, protocol 2 whenever `ready` advertises it with the standard limits, `glen_reply` registers, the event allowlist is accepted, `get_state`, `get_available_models` and `get_available_thinking_levels` decode, and stdin EOF ends omp within 10 s. It runs against `fake_omp` in CI and against a real omp with `GLEN_OMP_SURFACE_BIN`, always with its own scratch HOME as HOME and cwd. `tests/omp_source_facts.rs` checks 32 literal facts (`tests/fixtures/omp-surface/facts.json`: RPC commands and events, the duplicate-tool rule, CLI flags, lease path and name, session-owners and agent-dir names, the leaf, continuation, session version and title slot, and the `tools.approvalMode` setting doctor reads: its values and `yolo` default, the `config.yml`/`config.yaml` names, the invalid-value fallback, `PI_CONFIG_FILES` and the overlay-above-project merge order) against an omp source tree, read-only; the manifest's `omp` must equal `tested`, so a bump forces a re-check. ACP's `PROTOCOL_VERSION` is not yet one of the 32 (§A17 W6 candidate), so the nightly cannot see it move.
- **The nightly** (default 8). `.github/workflows/omp-latest.yml` runs at 04:41 UTC, on `workflow_dispatch`, and on any pull request that touches its own workflow file. It is separate from required CI, `permissions: contents: read`, references no secret, pins every action to a full SHA, and the release preflight never reads it. It installs the latest omp with the official installer (`--binary`) into a `mktemp -d` HOME under `env -i`, discovers the binary, copies the stub provider there, then runs the surface contract, the source facts (only the manifest's files, fetched from the installed version's tag), and `glen doctor --probe --json` from the scratch directory; every omp command has the scratch HOME. An `if: always()` summary names the omp version, each step's outcome, a "bump candidate" line when every step passed and glen's doctor `omp_version` row says `untested` (read with `jq`, not the shared `omp_version_untested` warning, which an unparseable version also raises), and what it does not cover: model turns, and lease and storage behaviour under a real turn. A scheduled workflow on a public repository is disabled after 60 days without commits; W6's dispatch and the summary make such a gap visible.

## §A20 Push to the calling agent
Owner: **v0.2 W2** (ADR `0773c35d`, plan `.claude/plans/v020-wave-2-push.md`). omp replies reach the calling agent without the agent running a `glen inbox` polling loop. Flags only: no new verb, no new crate, no visible command added.
- **Decided** (ADR `0773c35d`):
  - **What push means in v0.2.** No first-party mechanism lets an outside process wake an already-running, idle Claude Code or Codex session (research, 2026-11-01). Claude Code Channels is a research preview and is ignored under `-p` and in subagents. `asyncRewake` is broken headless. Codex hooks are outbound-only, and the visible session's App Server cannot be reached from outside. So push is a finite, one-shot receiver that the caller starts itself: when it exits, the caller wakes. Channels, `asyncRewake` and PTY injection are not foundations. "No polling" means no agent or model loop; glen may still watch its own files on a bounded interval.
  - **Wording**, defaults (4) and (5): release copy says "push" for Claude Code only and "blocking wait" for Codex. Headless and subagent wording follows W2's evidence (the table below). For Codex, the v0.2 headline means pending-tool delivery, a blocking wait; the CHANGELOG says "Codex: blocking wait, not push", so the goal is not silently redefined. There is no launch-owned caller adapter.
  - **Channels**: a hidden `glen mcp --channel`, decided in §A22. It is tested at the protocol level only and stays out of SKILL.md, README and the site.
- **Receivers**, default (7):
  - `glen wait <job> --for reply [--after <reply-id>]`. The job is the subscription: both routes append every `glen_reply` to `jobs/<id>/replies.ndjson` (RPC `src/rpc/reply.rs`, live `src/live/drive.rs`), so one reader serves both, the extension's inbox mirror is not read, and there is no caller registry. While the watch is active `observe` ticks every 100 ms with one `metadata` call, and re-reads the file only when its `(len, ino)` changed, through a complete-line reader that leaves a torn last line for the next tick. Each tick checks terminal status, child exit, the SIGINT flag, the reply poll and then the bound; a non-empty poll is followed by one more terminal check, and terminal wins, carrying every unseen reply.
  - `glen inbox --wait [--timeout DUR]` (default 90s, at most 24 h; conflicts with `-f` and `--all`) runs `inbox -f`'s `collect` every 250 ms, with the same `--session` and `--cwd` scope, for replies that arrive after the job ended and TUI messages with no job.
- **The unseen set.** A reply is unseen when its `id` is not in the seen set. With `--after X`, the seen set is the ids up to and including X in `replies.ndjson`, resolved once at start; without `--after` it is empty, so replies already present wake the call at once. An `--after` id that is not in the file is exit 2 `usage` with `details:{reason:"unknown_reply",job,after}`, never a silent "everything is unseen".
- **`wait --for reply` documents** (`docs/json.md` examples `wait.reply` and `wait.reply.expired`):
  - Reply wake: exit 10, `ok:true`, `data:{status:"running", woke:"reply", job, session, replies, next, interrupted:false}`. `replies` holds the unseen replies in file order (at least one); `next` is `glen wait <handle> --for reply --after <last id of this document>`, plus `--timeout <T>` when the caller's bound differs from the 90 s default; `job.task_state` is `working` or `submitted`.
  - Bound expiry: exit 10, the same keys without `woke`, `replies:[]`, and `next` = `glen wait <handle> --for reply`, plus ` --after <X>` when the caller passed `--after X`. SIGINT gives the same document with `interrupted:true`, exit 130.
  - Terminal: completed is exit 0 (11 when forked), the plain wait document with `data.replies` holding only the unseen replies. Failed `no_route` is exit 6; other failed, aborted and lost jobs are exit 7; both keep their envelope and add `error.details.replies` (the unseen replies, possibly empty). Plain `wait` and `send` documents are unchanged apart from `job.task_state` (§A7).
  - A reply-wake document can pass the spill threshold (replies reach 64 KiB); it then arrives as `spilled` (§A10), with `woke` and `next` inside the spilled file.
- **Two exit-10 documents.** Exit 10 still means the job continues (§A7, §A11). Under `--for reply`, a reply wake carries `woke:"reply"` and bound expiry does not, so a caller reads `woke` before treating exit 10 as a timeout, and runs `data.next`, whose `--after <last reply id>` keeps a woken reply from being seen twice. §A11, the `docs/json.md` exit row and the skill's exit table say so.
- **Replies and the inbox.** `wait` never touches the inbox read marker: a reply returned by `wait` stays unread in `glen inbox`. The reply id is `wait`'s cursor, so independent readers never consume each other's marker; concurrent inbox readers keep independent cursors and may deliver a record twice, but never lose one. A caller that reads both dedupes by `id`, as the skill says.
- **Late and TUI replies: `inbox --wait`.** The first tick with at least one record returns the normal inbox document, exit 0, and commits cursors after output unless `--peek`. When the bound passes with none, it exits 10 with `data:{total:0, marked_read:false, skipped_lines, messages:[], next, interrupted:false}` and marks nothing; `next` is `glen inbox --wait --timeout <T>` plus the caller's `--session`, `--cwd` and `--peek`, shell-quoted. SIGINT gives the same document with `interrupted:true`, exit 130; SIGTERM and SIGHUP keep their default disposition. With `--cwd`, a session glen cannot yet place in the project may wait for the 3 s catalog rescan (§A9 Inbox).
- **Per-caller delivery.** W2 keeps this table current:

| Caller | Delivery | Push |
|---|---|---|
| Claude Code, interactive | `glen send <h> "…" --no-wait`, then `glen wait <job> --for reply` as a background Bash task (`run_in_background`); its completion wakes the session | yes |
| Claude Code, `claude -p` | the same background wait, within the run; acceptance mode `p` (`tests/acceptance`) records whether its completion wakes the run, and the skill uses a foreground wait if it does not | yes (verified 2026-11-02 on Claude Code 2.1.316, stream-json: the completion notification resumed the run; the skill's allowed-tools may not apply to the resumed turn under dontAsk) |

## §A21 Warm worker
Owner: **v0.2 W4** (ADR `0773c35d`, plan `.claude/plans/v020-wave-4-warm-worker.md`). An opt-in warm worker that keeps omp alive for a bounded time after a settled job, so a following send to the same session skips omp's startup.

- **Decided** (ADR `0773c35d`):
  - Default (3): off by default (flag absent, or `0`). `send --warm DUR` beats `GLEN_WARM`, even `--warm 0` over a non-zero `GLEN_WARM`. The maximum is 10m (`warm::MAX_WARM`); a larger or unparsable value is `usage` for the flag and `invalid_env` naming `GLEN_WARM` for the variable, both before a job exists. `@new` sends may stay warm, keyed by the session id recorded at settlement.
  - Default (2): the warm worker keeps its omp client **and** glen's session lock, as lock-holder kind `warm` (`jobs::lock::HolderKind::Warm`); it never binds a live endpoint. `ctl::route::owner` reports `Owner::Warm` only while no active job of the session already names the holder's pid: right after a claim the holder already says `kind:"job"`, so a reader never sees `warm` paired with an already-claimed status.
- **Match key and `env_digest`.** A queued job is a candidate iff its route is `rpc`, its status is `queued`, unclaimed (`omp_reused:false`) and its `session_id` equals the warm session's. It is adopted iff `omp_bin`, `profile_flag`, `thinking_flag`, `cwd` and a present `env_digest` all equal the key of the job that made the worker warm; otherwise the worker cools and the candidate runs cold, with its own environment. `cwd` compares by canonicalising both sides (`std::fs::canonicalize`; lexical equality when either call fails), because a `@new --cwd` given through a symlink and the session header's own recorded `cwd` can name one directory two different ways. A job recorded without an `env_digest` (written before v0.2 W4) never goes warm and is never adopted.
  - `env_digest` is xxh64 (seed 0) of the sorted `KEY=VALUE` pairs of the send process's own environment, each name and value length-prefixed (a `u64` byte count ahead of the bytes, so no value can forge a second variable), excluding every `GLEN_` variable and `warm::VOLATILE_ENV` (`_`, `PWD`, `OLDPWD`, `SHLVL`, `COLUMNS`, `LINES`, `TERM_SESSION_ID`), rendered as 16 lowercase hex digits; only the digest is ever recorded, never a value (`job.json` is 0600 in the private home, §A6, but a 64-bit non-cryptographic hash of a low-entropy secret is still guessable). `Env::from_process` drops non-UTF-8 variables before the digest sees them, so such a variable can never make two otherwise-equal environments compare unequal: a known gap, and the safe direction, since a miss only runs the job cold. Every `FAKE_OMP_*` test knob counts toward the digest like any other variable (§A15).
  - `job.json` gains `warm_ms` (present only when the effective warm duration is above 0 on the `rpc` or `new` route) and `env_digest` (present on every `rpc` and `new` job regardless of `--warm`); live jobs record neither. `status.json` gains `omp_reused`, true only for a job that ran on an omp process a warm worker kept from an earlier job — the job that made the worker warm is itself `omp_reused:false`. Every job view (`send`, `wait`, `jobs`, error details) carries `omp_reused`.
- **Stay-warm rule.** After an `rpc` or `new` job, the worker stays warm only if all hold: `warm_ms` above 0; status `completed`; `result.session_settled` true; no `forked`; no cancel (`Worker::keep_warm`), which also excludes every failed, aborted, timed-out and completed-unsettled outcome. The idle window opens only once that terminal status is durable on disk — not at the completed result itself — and re-arms after each adopted job with **that job's own** `warm_ms`; a job without `warm_ms` ends warmth after it runs. The live route never stays warm.
- **Registry and release request** (`run/warm/<lock_key>.json`, `.release`; §A6). The idle registry is `{v:1,pid,start,session_id,session_handle,job_id,origin_job_id,omp_pid,omp_start,warm_ms,expires_at,state:"idle"|"busy",started_at}` (`origin_job_id`, the worker's own argv job, is what `--force` proves; §A14 S-09), published atomically (0600 in a 0700 directory) at every state transition; the heartbeat is the file's own mtime, touched every second while idle, never rewritten or fsynced. Stale means `state:"idle"`, the worker's pid and start token still matching (proven alive), and the mtime older than 5s (`warm::STALE`; debug builds read `GLEN_WARM_STALE_MS`, 100–30000, to shorten it for tests); dead means the pid or start token no longer match (an `Unknown` liveness still counts as alive, as everywhere in glen — only a proven change is dead; a busy worker is never stale, since it heartbeats only while idle). The release request (`<lock_key>.release`) holds `<pid>:<start token>` of the worker it targets; a worker honours only a request naming its own identity, so one meant for an earlier worker of the session (left by a crash, or written just as that worker cooled) is ignored rather than cooling its successor. Both files are removed only by whichever worker's identity they still name, at teardown. Every publication and removal of either file (the worker's own, at teardown too, and `glen release`'s conditional ones) runs under the session's metadata lock, `<lock_key>.lock`: a flock independent of the session lock, held only for that one read, compare and write or unlink and waited for at most 1s (teardown takes it once for both of its removals), so a conditional removal unlinks exactly the file whose identity it compared and no file is ever moved aside or put back. The lock file lives only while a file it guards does (its last holder unlinks it, and a lock taken on an unlinked file is retried); the heartbeat takes no lock, since it never creates the file; and a release request whose lock stays busy past the bound (a stopped holder) is not written and is reported unwritten, so `glen release` never calls that worker `cooling` and falls to its timeout or `--force`.
- **Claim protocol.** The idle loop scans every 100ms (`warm::CLAIM_TICK`) for the oldest queued, unclaimed `rpc` job of its session; a cache of already-classified ids keeps a quiet tick to one `read_dir`, and a job directory caught mid-`create` (one file written, not the other) is retried for up to 2s rather than cached irrelevant, since AC-v2-402's 500ms bound forbids a false negative. Adoption, in order: a bounded (1s) `get_state` confirms omp still drives the expected session; the lock holder is marked `kind:"job"` for the candidate **before** the compare-and-claim write, so a reader of the holder never sees `warm` paired with an already-claimed status; then the claim itself, under the job's status lock, sets `worker_pid`/`worker_start` to the warm worker's own and `omp_reused:true` only while the job is still `queued` and unclaimed — the same write that moves the job's liveness from its blocked cold worker to the claimant. A lost race (another process claimed first) re-marks the holder `warm` and the scan continues next tick. A claim that lands runs on the warm omp with a fresh `ReplySink`, its own event/reply drain as a barrier against the previous job, and its own bounded `catch_unwind`, so a panic in an adopted job fails only that job (`finish_failure`), never the job that made the worker warm. Every status write a `Worker` makes — including a timeout, a forced failure or a panic — is refused once the on-disk status names another worker's pid, so a blocked cold worker can never clobber a job a warm worker already claimed; a refused worker exits 0 with a `worker.log` line and no status write. The reader's loss check (`jobs::wait::observe_with`, `liveness::mark_lost_unless_claimed`) keeps watching, under the same status lock, rather than marking a child-exited job lost while its on-disk `worker_pid` still names a different, live process, and marks it lost as before once that process is proven gone.
  - **Queued-job liveness** (the decision this section records, per the W0 review finding): the cold `__worker`, which already writes its pid before the lock wait, stays the queued job's liveness holder, and the claim above replaces that identity with the claimant's in one status write. Rejected: exempting an unclaimed job from loss detection would leave a dead cold worker undetected; writing the warm worker's pid at enqueue would need the sender to already know which worker is warm.
  - Idle-loop order, each tick: the cancel flag (SIGTERM/SIGHUP/SIGINT) → whether omp's event channel disconnected (omp exited) → draining any `glen_reply` that arrived while idle, rejected with a tool error attributed to no job (`PendingReply::discard`) → a release request addressed to this worker → a live endpoint registry for the session (a stat, then one read; a live pid or an unreadable file yields, a dead one is ignored — never a hello probe, which alone could spend the whole 1s budget) → expiry. The first of these ends warmth through one teardown; otherwise the heartbeat is touched at most once a second and the claim scan runs. A stray control request addressed to the job that just ended is answered `job_ended` on every tick.
- **Teardown** is one function for every ending, logging `warm: cooling (<reason>)` to `worker.log` (reasons `expired`, `release`, `endpoint`, `signal`, `omp_exited`, `mismatch`, `moved`, `state_error`, `ended`): `Client::close` (SIGTERM 1s, SIGKILL 1s, reader join 1s — omp-rpc's own constants, so at most 4s) runs on a helper thread bounded at 3.5s (`warm::TEARDOWN_BOUND`); on the normal path, where the group exits on SIGTERM, it takes under about 1.1s, and on the rare path where it does not, teardown still removes the registry and the release file, then drops the lock, logging that the omp group may survive — so a later send meets a truthful lease-probe refusal, never a hang. Teardown has one deadline, 3.6s from its start (`warm::TEARDOWN_DEADLINE`): after the close it removes the registry and the release request under a single acquisition of the metadata lock, waited for at most 1s and never past that deadline, then frees the session lock, so the session lock is free at most about 3.6s after teardown starts on every path. Normally the metadata lock is free or held for one step, so both files are gone before the lock and a reader never sees a free lock with a live registry. The one exception is a metadata-lock holder that keeps it past that wait (a process stopped while holding it): teardown then logs `cannot remove … (the session lock is freed anyway)` and frees the session lock with both files still on disk. Until the worker exits, right after teardown, a reader can then see a free lock with a registry that still reads idle; after that the registry names a dead process (`dead` in `ls` and doctor), a successor's own publish waits for the same metadata lock, and `glen release` removes the leftovers (`cleaned`) once the holder lets go.
- **`glen release [<target>] [--all] [--force] [--timeout DUR]`.** Exactly one of `<target>` (a session id, a hex tail of 4 or more, or a job handle — matched against `run/warm/` entries only; a `@new` job's worker is found by its settled `actual_session_id` even after a follow-up job was later adopted onto it) and `--all`. Per entry: a dead one (pid or start token proven changed) is removed and reported `cleaned`, never signalled; a busy one gets a release request and returns at once, `cooling` (it cools after that job), but only once the request is written: a request the metadata lock keeps out (held past its 1s bound by a stopped holder) is never reported `cooling`, and that worker is handled like one that never answers (the `--timeout` wait, then `--force` or `release_timeout`); an idle, responsive one gets the request and waits until the lock is free and the registry gone, `released`; a stale heartbeat under `--force` is killed at once; otherwise `--force` waits `--timeout` (default 10s) then kills. `--force` only ever signals a proven identity: the worker's pid and start token, and omp's own when recorded, must both be alive (an `Unknown` liveness — a live pid with no recorded start token — is never signalled; the registry is kept and the attempt falls to `release_timeout`), and the process image, argv and ancestry must show the session's glen worker and its omp (§A14 S-09; otherwise the row carries `reason:"unverified_process"`). A removal of a dead worker's files (`cleaned`, or after a `--force` kill, `forced`) whose metadata lock stays busy past its bound removes nothing more and is `release_timeout` too, with the files kept for a later run; a successor's files it spares are still success. A worker that does not release in time without `--force` is exit 7 `control_failed`, `details:{reason:"release_timeout",workers:[...]}`; no match for `<target>` is exit 3 `not_found`, `details:{reason:"not_warm",target}`. It creates no `GLEN_HOME` and never signals an entry whose identity it has not itself verified in this run.
- **Controls on a warm session.** `abort` reports `was:"idle"`, `aborted:false` and leaves the worker, registry, omp and lock untouched — no lease probe, no cooling. Every other control (`model`, `thinking`, `compact`, `models <session>`) writes a release request addressed to the holder's own identity, waits until the lock is free (or held by someone else), then continues the route loop exactly as if the session had never been warm. The refusal for another held RPC job names `glen release <handle>` as an alternative when the holder is a warm worker, alongside the ordinary job-holder wording (§A4).
- **`ls` and doctor.** `glen ls --json` sets `state_detail` to `warm worker, idle, <N>s left`, `warm worker, busy` or `warm worker, no heartbeat for <N>s` for a session with a live registry (read-only, from `run/warm` alone, never a probe); the human state cell gains ` (warm)` (` (warm, stale)` when stale). `glen doctor`'s `warm_workers` check sits right after `live_endpoints`: `<w> warm, <s> stale, <d> dead`, `info` when nothing is stale or unreadable, else `warn` naming the stale handle(s) and `glen release <handle> --force`; it never fails doctor (§A9, §A10).
- **Lease cost.** A warm omp child keeps holding omp's own owner lease between jobs, so the omp TUI cannot open that session until the window ends or `glen release` ends it early; `ls`/`show`/`tail` still read it as `live` or `busy` from the ordinary lease probe, with the warm `state_detail` layered on top.
- **Two residual races**, both accepted:
  1. The §A4 residual race (a TUI without the glen extension opening between a lease probe and omp's first write) narrows, while a worker is warm, to the width of one claim tick (100ms, the same period as the endpoint check) rather than closing: an extension-less TUI can still win it in that window.
  2. A `glen_reply` or `session_settled` frame already in flight in omp at the instant the next adopted job's prompt is submitted cannot be told from that job's own reply or settlement; the idle-tick drain and the per-job barrier close the gap for everything that arrives while genuinely idle, not for a frame already on its way in when the next job starts.
  - Also accepted: a `glen release` sent before a worker first publishes its registry finds no worker (`--all` total 0, a target `not_warm`) and the worker stays warm for its full window.
  - A control or a `send` against a SIGSTOPped warm worker waits out its own deadline (the control's `--timeout`, or the job's `GLEN_JOB_TIMEOUT`) rather than failing fast, because a stale heartbeat alone never frees the lock; `glen release <handle> --force` is the remedy.
- `--warm` and `glen release` were hidden until this wave's merge (Step 11), when `VISIBLE` moved from 18 to 19 entries and `DOCTOR_CHECKS` from 13 to 14 (§A9, §A10, §A16).

## §A22 MCP layer
Owner: **v0.2 W5** (ADR `0773c35d`, plan `.claude/plans/v020-wave-5-mcp.md`). An MCP server generated from `docs/json.md`, so the CLI and the skill stay the primary contract and there is one source of truth for every tool's shape.

- **Scope and decided points** (ADR `0773c35d`):
  - `glen mcp` is a synchronous stdio MCP server with no new crates (no tokio, no rmcp). It handles `initialize` with version negotiation, `tools/list`, `tools/call` and `ping`.
  - Each tool call runs glen itself (`current_exe`, argv, `--json`, never a shell), so every tool result is the CLI's own envelope: `isError` is `!ok`, and exits 10, 11 and 130 (running, forked, interrupted) are ordinary successful results. Streaming, TTY-only and installer commands are not tools.
  - The catalog `src/mcp/tools.json` is generated from `<!-- mcp: … -->` annotations in `docs/json.md` plus clap, checked in, and guarded by a drift test. Graft (AC-v2-506): input schemas come only from clap; no type, enum or requiredness is inferred from `docs/json.md` examples; `outputSchema` appears only where an annotation declares it.
  - Graft (AC-v2-502): cancelling a tool call (`notifications/cancelled`) stops the exec-self child. The job continues, and no abort is sent.
  - Default (1): a hidden `--channel` flag emits one `notifications/claude/channel` per new reply. It is peek-only and labels the content as omp output (untrusted). It is tested at the protocol level only, stays out of SKILL.md, README and the site, and is not a release blocker. The owner verifies it interactively after v0.2.0.
  - `mcp` is visible from this wave's merge, between `watch` and `install-extension` (§A9, §A16); the hidden `--channel` flag stays hidden.

- **Handshake and versions.** Legacy-era `initialize` only: `2025-11-25` and `2025-06-18`, both without JSON-RPC batching (which `2025-06-18`'s changelog removed; earlier revisions require servers to accept batches, which glen does not implement). A request naming either supported version is echoed back; any other value gets `2025-11-25`; a missing or non-string `protocolVersion` is `-32602`. The result carries `capabilities:{tools:{}}` and `serverInfo:{name:"glen",title:"glen",version:<crate version>}`; with `--channel` it adds `capabilities.experimental["claude/channel"]:{}` and an `instructions` string. A second `initialize`, or a `tools/list`/`tools/call` before the first one, is `-32600` naming the supported versions; `ping` works before `initialize`. The stateless 2026-07-28 revision (`server/discover`, no `initialize`) is **not implemented**: `server/discover` answers `-32601`, so a dual-era client's probe falls back to `initialize` and talks to glen normally, but a modern-only client cannot use this server at all. That is a scope line, not a bug (§A17 tracks re-verifying which era Claude Code and Codex actually speak on every upgrade).

- **Methods and errors.**

| Method / notification | Behaviour |
|---|---|
| `initialize` | version negotiation, `capabilities`, `serverInfo` (above) |
| `tools/list` | the catalog's tools (`name`, `description`, `inputSchema`, `outputSchema` only where declared), in catalog order; `cursor` is ignored and no `nextCursor` is returned |
| `tools/call` | validates the arguments, execs the child, maps the result (below) |
| `ping` | answers `{}` at once, even with a call in flight |
| `notifications/cancelled` | cancels one in-flight `tools/call` (below); ignored for an unknown or already-answered id |
| an unknown method (`server/discover` included) | `-32601` |
| an unknown notification | ignored |
| a message whose `jsonrpc` is not exactly `"2.0"` | `-32600`, with the message's own `id` when it is a valid string or integer, else `null`; checked before anything else, so a notification shaped this way is answered too but its action never runs |
| a line that is not JSON | `-32700`, `id:null` |
| a JSON array (a batch) | `-32600` |
| a line over 4 MiB | `-32700`, `id:null`; the server keeps serving |
| non-object `params` | `-32602` |
| a second `tools/call` naming an id already in flight | `-32600` |

- **Annotation grammar and the catalog.** One line `<!-- mcp: VERB [key=value …] -->`, the first line of a command's `docs/json.md` section: `tool` (keys `omit=<property>[,<property>…]`, `about="<text>"`, `note="<text>"`, `output='<JSON object>'`) or `skip` (key `reason=tty|installer|shell-setup|server|alias|help`). Every visible command, visible alias and `help` section needs exactly one; an unknown command, an unknown verb or key, or a repeat fails generation. The generator (`src/mcp/catalog.rs::generate`) reads `docs/json.md` and clap only — never a `<!-- contract: -->` example — and writes `src/mcp/tools.json` (checked in, pretty JSON, no glen version or timestamp, so a version bump never touches it): 14 tools in clap declaration order (`glen_ls`, `glen_show`, `glen_tail`, `glen_send`, `glen_wait`, `glen_jobs`, `glen_abort`, `glen_models`, `glen_model`, `glen_thinking`, `glen_compact`, `glen_inbox`, `glen_release`, `glen_doctor`) plus the recorded skips (`stop`, `watch`, `install-extension`, `install-skill`, `completions`, `mcp`, `help`). `__acp` and `__worker` appear in no annotation, tool or skip entry. `cargo test --locked --test mcp_contract regenerate_catalog -- --ignored` regenerates the file; `cargo test --locked --test mcp_contract` fails, naming that command, on drift in either source.

- **Naming and schema.** A tool is `glen_<command>`. A property is the argument's long flag with `-` as `_` (`--no-wait` → `no_wait`, `--as` → `as`), or a positional's clap id (`session`, `message`, `job`, `target`, `level`, `model`). The global flags `--json`, `--human`, `--color` and `--profile`, plus `--help` and `--version`, are never properties: a call always runs under the server's own profile. Every property's `type`, `enum`, `default` and `description`, and every `required` entry, comes from clap alone (the value-parser's type id, `ValueEnum` possible values, default values, help text, `Arg::is_required_set`) — never from a `docs/json.md` example, so rewriting every example leaves the catalog byte-identical. `omit` drops a property from a tool's schema (`tail` and `inbox` omit `follow`, the streaming form); `Append`, `Count` and a property-name collision fail generation rather than guess a shape. `outputSchema` appears only where a `tool` annotation's `output=` declares one; **no tool declares one in v0.2.0**, so no result carries `structuredContent`. A tool's `description` is clap's own `about` text unless the section's `about=` overrides it — CLI wording a tool cannot use, such as a reference to a `--flag` the tool omits; a `note=` is then appended as its own sentence: joined with `. ` when the description does not already end in a period, or a single space when it does. Two notes (on `send` and `wait`) document the 90 s defaults for a host that cuts tool calls sooner, and (on `send`) that `-` is not available as a message and one over about 100 KiB cannot be passed.

- **Execution.** A call's argv is `--json`, then `--profile=<p>` when `glen mcp` itself was given one, then the subcommand, then each supplied property in catalog order (a flag → `--long`; an option → `--long=value`), then `--`, then positionals in position order. An unset or `false` property is simply omitted, so **the child never sees a default the CLI would apply** — the server forwards exactly what the host sent and never adds or strips an argument. This is deliberate even where it produces a CLI refusal: a host that fills schema defaults and calls `send` with both `no_wait:true` and the schema's advertised `default:"90s"` for `wait` gets the CLI's own `usage` envelope for the conflicting flags, because both reach the child (no server-side argument stripping is planned; see Risks in the W5 plan). The child's stdin is `/dev/null` (so a `message` of `-` is the CLI's own usage error), and its cwd and environment are the server's own. A single argument over the platform's exec limit (Linux: 128 KiB) cannot be spawned at all; that is `mcp_exec`, worded "argument too long to pass to glen", not a hang.

- **Validation and results.** Absent or `null` arguments count as `{}`; `null` for an optional property is unset. An unknown key, a wrong JSON type, an enum miss, a missing required property or a NUL in a string is caught before any child starts: `isError:true` with `{"v":1,"ok":false,"error":{"code":"usage","message":…,"details":{"reason":"mcp_arguments","tool":…,"argument":…}}}`. Otherwise a result's `content` is exactly one `text` item: the child's stdout byte for byte. `isError` is `!ok`, following the envelope, not the exit status — a deferred `inbox` cursor failure (`ok:true` with exit 6 or 1, §A10) is `isError:false`, and its messages come back on the next read. A child that cannot start (an argument too long, or any other spawn failure), exits without a parseable JSON envelope, prints non-UTF-8 or more than 16 MiB of stdout, or finds 16 calls already running gets `{"code":"internal","details":{"reason":"mcp_exec","tool":…}}` plus `stderr` (the end of what the child printed there) when it printed any; the server keeps serving either way.

- **Cancellation and shutdown.** `notifications/cancelled` for an in-flight `tools/call` sends SIGINT to the exec-self child at once and SIGKILL `CANCEL_GRACE` (400 ms) later if it is still alive, then sends no response for that request; a call holds its registry slot until its answer is queued, not merely produced, so at most `MAX_IN_FLIGHT` calls can ever be waiting on a host that stopped reading. The job the call started keeps running and is never aborted (`glen jobs` and `glen wait` still find it running), because glen's own observers (`send`, `wait`) answer SIGINT with their ordinary interrupted exit rather than tearing down the job. A cancel naming an unknown or already-answered id is ignored. Shutdown is a separate, harsher path: on stdin EOF, a stdout write error (EPIPE, which counts as EOF), a host that leaves too much output unread (Limits, below), or SIGINT/SIGTERM/SIGHUP, the server SIGKILLs every in-flight call's child at once — no `CANCEL_GRACE` — then joins the call threads for at most `SHUTDOWN_JOIN` (1 s) and exits 0 (EOF) or 130/143/129. `glen mcp` given a TTY stdin is `usage` (exit 2, hinting `claude mcp add glen -- glen mcp`); stdout carries protocol messages only, so this and every other refusal (including a catalog parse failure, or any clap usage diagnostic) goes to stderr as text, never a JSON envelope on stdout, even with `--json` (`OutputKind::Protocol`, always raw, unlike every other command). On Linux, if `current_exe()` reads `… (deleted)` (the binary was replaced while the server runs), the server execs `/proc/self/exe` instead, so an upgrade in place never strands a running server.

- **Limits.** 4 MiB per protocol line, 16 MiB of a tool call's child stdout — past it the pipe is closed, not drained, so a grandchild still writing meets EPIPE instead of an endless reader — 16 concurrent calls (a 17th gets the `mcp_exec` envelope at once; a call holds its slot until its answer is queued, so a host that stops reading cannot free one early), 8 KiB of channel notification content. One dedicated writer thread owns every stdout write, queuing messages from calls and the notifier in order: once 32 MiB is queued and still unread, a call or the notifier waits for the host to catch up (shutdown cuts that wait short); past 64 MiB unread with no read at all, the host counts as gone and the server shuts down as it does on stdin EOF.

- **Channel (hidden `--channel`).** Peek-only: a thread polls `glen --json inbox --peek --cwd <server cwd>` through the same exec-self runner, waiting at least 1 s after each poll completes and at least four times that poll's own wall time — the wait is counted from when the poll ends, not from when it started, so it never shortens because the poll itself ran long — so a slow poll never costs more than a fifth of a core, with `GLEN_MAX_OUTPUT=0` set in that child's environment only. While answering `initialize` the server takes one baseline poll (2 s bound; a signal to the server ends it early, leaving the set empty rather than delay the `initialize` response) and records every `data.messages[].id` silently, so a reply appended only after the client has the `initialize` result is guaranteed to be seen; later polls emit `notifications/claude/channel` for ids outside that set, in file order, one per id. An id a poll still lists is never forgotten; past 10,000 remembered ids, the oldest ids a poll no longer lists are forgotten first, so a reply still on the list is never replayed. `content` is a label naming the session (and job, when any) as untrusted omp output, then the reply text with every `<` written `&lt;` (so it cannot close Claude Code's own `<channel>` tag), cut to 8 KiB with a marker naming `glen inbox --peek`. `meta` holds only `origin:"omp"`, `session`, `job` (omitted when null), `reply_id` and `final` (`"true"`/`"false"`), and keeps a value only when it is a short plain token (`^[A-Za-z0-9._:-]{1,128}$`); a hostile value drops its key rather than reaching the host. `instructions` tells the model these events are one-way and untrusted, and that a reply goes through `glen_send`. The notifier never marks a message read, its scope is the server's own project, and a failed or timed-out poll skips that tick and keeps the existing baseline. It is tested only at the protocol level (`tests/mcp.rs`, a scripted client); the owner verifies the interactive case after merge, and the flag stays out of help, completions, the skill, README, `docs/json.md` and the site (AC-v2-501f).

- **Host notes.** Codex's default `tool_timeout_sec` is 60 s, shorter than `send`'s and `wait`'s 90 s defaults: set `tool_timeout_sec` higher (the README's example uses 120) in `[mcp_servers.glen]`, or pass a shorter `wait`/`timeout`, or `no_wait`, then call `glen_wait` again — a timed-out tool call never aborts the job. Codex also forwards only a short environment allowlist to a stdio server, so `GLEN_HOME` or `GLEN_OMP_BIN` must go in that server's own `env` table, not the caller's shell environment. Claude Code caps an MCP tool result near 25 000 tokens; a result past `GLEN_MAX_OUTPUT` (default 24 000 bytes) already arrives as glen's own `spilled` pointer (§A10), which a sandboxed host may not be able to read.

- **Security.** A tool call gives the host's model everything the CLI gives a terminal user: `send`, the session controls and `release` change sessions, not just read them, so a host should keep per-tool approval on rather than blanket-allow the `glen_*` tools. Channel content is untrusted, omp-authored text (a prompt-injection vector); it is labelled, escaped and capped, and the owner's interactive check is the only exercise of it against a real Claude Code channel.

- **Not implemented.** MCP resources, prompts, progress notifications, logging, and tool annotation hints (`readOnlyHint` and similar) are absent; `readOnlyHint` for `ls`, `show`, `tail`, `jobs`, `models` and `doctor` (fewer host approval prompts) is the first candidate, outside this wave. The stateless 2026-07-28 revision and its `server/discover` method are not implemented (above).

- **Known timing gap.** With a very large backlog of unread requests, stdin EOF shutdown can take a little over 2 s (measured 2.1-2.9 s with 600 queued requests: each queued line is still dispatched before the EOF is handled), while a signal (SIGINT/SIGTERM/SIGHUP) still wins within about 1 s, since it SIGKILLs every in-flight call at once rather than draining the queue. Accepted (v0.2 W6 tech-debt audit): a host that floods the pipe and then disconnects sees a slightly slower EOF exit, never a hang, and a signal remains the fast path.

## §A23 ACP spike
Owner: **v0.2 W3** (ADR `0773c35d`, plan `.claude/plans/v020-wave-3-acp-spike.md`). A spike of `omp acp` (Agent Client Protocol v1) as an optional second transport. It is a spike, not a rewrite: the RPC driver stays, and ACP stays out of production routing.

**Result:** GO, scoped (2026-11-02; evidence `.claude/evidence/v020-wave-3-acp-spike/20261102T1136Z/`, `verdict.md`). `omp acp` is a viable optional second transport for sends that need no `glen_reply`; it is not a replacement for the RPC route and not a route to the push headline. `session/load` neither holds nor checks the owner lease, so glen's pre-spawn guard is the only protection against a live owner. ACP v1 gives no `glen_reply` attribution, no fork detection (no exit 11) and no settlement events; omp reports an assistant `error` stop as `end_turn`, so only a transcript comparison shows a failed model turn. The command stays hidden.

**What ships.** A hidden `glen __acp <session|@new> <message> [--permission allow|deny]` (`src/commands/acp.rs`) on a hand-rolled, synchronous ACP v1 client (`src/acp/`): a reader thread and a writer thread over the child's stdio, no tokio, no ACP crate, no new crate. It is not a contract: it is absent from `--help`, completions, SKILL.md, `docs/json.md` and any MCP catalog, its document is described only here, and it may change or go away without notice.

**Decided** (ADR `0773c35d`):
- `__acp` never appears in help, completions, SKILL.md, `docs/json.md` or the MCP catalog. It is in the conformance `HIDDEN` set and has a help page (`glen __acp --help`, `glen help __acp`).
- It takes glen's session lock and runs the endpoint and lease probes, refusing with exit 6 like an RPC resume. It runs omp with `GLEN_MANAGED=1`, writes no `.jsonl`, and creates no durable job: `GLEN_HOME` gains only `run/locks/<key>.lock`, never `jobs/` or `inbox/`.
- A negative result completes the spike. There is no `glen_reply` parity claim: the losses below record the loss of reply attribution under ACP. The outcome is an ADR with a go/no-go.
- `input_required` (§A7) appears only in `__acp` events, one per permission request omp sends.

A `cancelled` prompt response confirms acceptance, not finished cleanup, so `cancel.confirmed` means accepted. `stopReason` is a field of the correlated `session/prompt` response (`protocol.ts:360-363`), never of a `session/update`: glen rebuilds the text from the updates and takes `stop_reason` from the response. No completion notification is invented.

**How `__acp` works.**
1. Validate the message (empty or over 512 KiB is `usage`, before anything else). Refuse in a sandbox (`refuse_unreachable`, then `refuse_rpc`: ACP never takes the live route). Resolve the session (handle, id or `@latest`) unless it is `@new`; omp runs in the header's cwd when it is a directory, else in glen's cwd. Resolve `GLEN_HOME`. The deadline is `GLEN_JOB_TIMEOUT` (default 60m; its `invalid_env` warning is kept).
2. An existing session gets the guard of `Ephemeral::open_session`, in its order: `lock::try_acquire` (held: exit 6 `rpc_job_running`, with a hint to wait for `glen jobs --active --session <handle>`); mark the holder `control`; follow continuations and re-read (a changed id is `control_failed` `session_moved`); `live::route::find` with the 1 s hello probe (a live endpoint is exit 6 `live_owner` with the hint `use glen send <handle> (the live route); __acp never joins a live session`, an unhealthy one is `unhealthy_endpoint`, and a not-yet-persisted session with no endpoint is `endpoint_gone`); then `refuse_hidden_lease`, the lease probe and `map_probe_failure`, and `live_owner` or `unknown_lease` unless the lease is free. Every refusal comes before omp starts.
3. Find omp (`GLEN_OMP_BIN`; missing is exit 5 `acp_spawn`), install the SIGINT, SIGTERM and SIGHUP flag, and spawn `omp acp [--profile NAME]` in the cwd, in its own process group, with `GLEN_MANAGED=1` (an explicit profile drops `OMP_PROFILE` and `PI_PROFILE`). omp's stderr is drained (16 lines of 1024 bytes) and reported as `details.stderr` on failures only.
4. `initialize` with `protocolVersion:1`, `clientCapabilities:{fs:{readTextFile:false,writeTextFile:false},terminal:false}` and `clientInfo:{name:"glen",title:"glen",version}`. The result's `protocolVersion` must be the integer 1; an existing session also needs `agentCapabilities.loadSession:true`. `agentInfo.{name,version}` becomes `data.agent`.
5. `@new`: `session/new {cwd, mcpServers:[]}`. Its non-empty `sessionId` is locked right after the answer, as the RPC worker locks an id omp reveals (§A3); a lock already held there is an `io` error. An existing session: `session/load {sessionId, cwd, mcpServers:[]}` with an absolute cwd.
6. `session/prompt {sessionId, prompt:[{type:"text",text}]}`. Agent requests are answered inline: `session/request_permission` by the policy, every other request (`fs/*`, `terminal/*`, `elicitation/create`) with -32601. Unknown notifications, `$/cancel_request` included, are ignored.
7. After a turn omp answered without a glen cancel, `session/close` (2 s, best effort, warning `acp_close_failed`) when omp advertises it; then stdin EOF and the bounded teardown. The session lock is released only after the process group is gone.

Frames: requests carry integer ids from 1. A frame with `method` is a request (with `id`) or a notification (without); one with `result` or `error` and no `method` is a response, matched by exact id type and value, so an agent request that reuses an id never completes a call. A frame over 16 MiB, invalid UTF-8, invalid JSON, a non-object, a wrong `jsonrpc` or a frame that is none of the three is malformed; blank lines are skipped, as omp skips them.

**Text rebuild.** Only `session/update` notifications for the session that are processed after the prompt frame is queued count. Chunks are `agent_message_chunk` with text content, grouped by `messageId`; a chunk without one joins the current anonymous group, and a `tool_call` or `user_message_chunk` closes it. `assistant_text` is the last non-empty group (the RPC route's "last assistant text"), `null` when none, capped at 4 MiB (`text_truncated:true`). Updates processed before the turn (history replay, bootstrap) are counted as `updates.replayed`. After the prompt response glen keeps processing frames for one more 100 ms tick, so an update that overtook the response is not lost.

**Permission.** `allow` answers the offered `allow_once` and `deny` (the default) the offered `reject_once`, never an `*_always` option (omp caches those per session). When the wanted kind is not offered the answer is `{"outcome":{"outcome":"cancelled"}}`. Once glen has written `session/cancel` (signal or deadline), every permission request is answered `cancelled`, whatever `--permission` says. The job deadline stays the cutoff during `session/close`: its own 2 s bound may outlast the deadline, but a request after the deadline is answered `cancelled`. Each request adds `{event:"task_state", task_state:"input_required", tool_call_id, title, kind, policy:"allow"|"deny", answer:"allow_once"|"reject_once"|"cancelled", option_id}` to `data.events` (at most 100; `events_dropped` counts the rest).

**The document** (hidden; not in `docs/json.md`): `data:{transport:"acp", protocol_version:1, agent:{name,version}|null, permission, session:{id,handle,path|null,created}, task_state, stop_reason, assistant_text, text_truncated, events, events_dropped, updates:{replayed, during_turn, messages, kinds}, usage, cancel}`. `messages` counts the non-empty assistant groups of the turn, and `kinds` counts the turn's updates by `sessionUpdate`. `end_turn` is `completed` and exit 0; `cancelled` is `canceled`; `refusal` is `rejected`; `max_tokens`, `max_turn_requests` and any other value are `failed`, with the raw value kept in `stop_reason`.

**Signals.** SIGINT, SIGTERM or SIGHUP during the turn writes one `session/cancel` within 250 ms and waits up to 5 s for the prompt response. The result is an `ok:true` document with `task_state:"canceled"`, `cancel:{sent:true, confirmed, reason:"interrupt"}` and exit 130; `stop_reason` is omp's answer (`cancelled` when it confirmed) and `null` when none came. Before the prompt there is nothing to cancel: `cancel` is `{sent:false,confirmed:false,reason:"interrupt"}` and the group is stopped with a 100 ms grace. A second signal exits at once and leaves omp's group to its own stdin EOF handling, as the session controls do (§A4; the W8-ERR-3 residual).

**Failures.** Every error repeats `session`, `events`, `assistant_text`, `stop_reason`, `task_state`, `cancel` and `stderr` in `details` when they exist.

| When | Exit / code | `details.reason` |
|---|---|---|

| EOF or exit before the `initialize` result | 5 | `acp_exited` (+ `stderr`) |
| `initialize` not answered in time | 5 | `acp_timeout` |
| `initialize` error response, `protocolVersion` missing, not an integer or not 1 | 5 | `acp_protocol` (+ `requested:1`, `got`) |

| EOF or exit after the `initialize` result | 7 | `acp_exited` |

|---|---|

| `initialize`, `session/new`, `session/load` | each `min(60 s, time left)`; debug builds read `GLEN_ACP_SETUP_MS` (100 to 60000) |
| `session/prompt` | the job deadline |

**Experiments** (Step 7: real `omp acp --profile glen-harness` in `$TMPDIR` scratch sessions, never the owner's default agent dir; two real turns in total, no reruns):
- **E3** (turn 1, creates the scratch session S): `__acp @new "Reply with exactly: acp-e3-ok"`, compared with S's transcript read after `__acp` exited. Result: pass; exit 0, `end_turn`, text `acp-e3-ok`, transcript assistant `stop`, 5 update kinds seen.
- **E1** (no model call): does `omp acp` hold S's owner lease between `session/load` and the first write; what does `session/load` do while another process holds the lease; and does `__acp` refuse with exit 6 `live_owner` before any spawn (E1(c) points glen at `fake_omp`, so a broken guard reaches only the fake). Result: `omp acp` held no lease after `session/load` (session stayed `idle` for 8 s); `session/load` succeeded against a foreign holder (no error, no fork); `__acp` refused with exit 6 `live_owner` before any spawn. `omp acp` needed SIGTERM after stdin EOF.
- **E2** (turn 2, loads S): one delete-tool call under `--permission allow`. Branch R (at least one `input_required` event) or Branch Z (none: the profile's approval policy, which denies `bash`, `edit` and `delete`, pre-empts the ACP gate). Result: Branch Z; the model never attempted a tool (answered `acp-e2-blocked`, exit 0, `end_turn`, file untouched), so the allow path through real omp was not exercised.

**The rule, fixed before the runs.** GO (ACP is a viable optional second transport) only if all hold: (G1) E3 matches on every point (the last assistant text equals `assistant_text`, `stop_reason` is `end_turn`, `updates.kinds` has an `agent_message_chunk`, and the transcript's assistant `stop_reason` is not `error`, `aborted` or `length`); (G2) E2's turn ended `end_turn`, a request (if any) shows the answered `allow_once` and no error caused by a missing answer, and the transcript's last assistant `stop_reason` in `e2-show.json` is not `error`, `aborted` or `length`, because omp reports an assistant `error` as `end_turn`; (G3) the E1 observations are recorded and E1(c)'s refusal held. E1 never fails GO by itself: it sets the scope line. NO-GO if G1 or G2 fails. A turn that could not run (a provider refusal, no login, a provider error in the transcript) makes the verdict "inconclusive, no GO claimed" and AC-v2-304 blocked. Applied: G1, G2 and G3 pass; verdict GO, scoped.

**Losses under ACP v1.** Regardless of the verdict they bound any GO to "sends that need no `glen_reply`", never "replacement of the RPC route" or "the push headline":
- No `glen_reply` attribution. `GLEN_MANAGED=1` registers no tool, and ACP v1 has no host-tool registration. With `GLEN_MANAGED` unset the extension's tool would write `inbox/<session>.ndjson` with a null job id and nothing in `jobs/<id>/replies.ndjson`, so `wait --for reply` could never see it. The only conceivable path is a client-supplied MCP server in `session/new.mcpServers`, unproven.
- No fork detection, so no exit 11: ACP has no `get_state`, and the `session/load` answer carries no id.
- No `session_settled`, no `agentInvoked` and no `command_output`.
- Controls are only `session/cancel` and `session/set_config_option`; there is no steer or follow-up delivery beyond omp's non-standard `_session/steering`.
- ACP `end_turn` cannot distinguish a failed model turn: omp maps an assistant `error` to `end_turn` unless it matches content-filter or refusal, so only a transcript comparison can.

**Limits.** A post-load `agent_message_chunk` notice is indistinguishable from turn text. A message that starts with `/` reaches omp's ACP slash-command layer; the spike does not escape it. `session/resume` would avoid the history replay (and the 60 s setup bound on a huge transcript) and is the first refinement if GO. The guard mirrors `Ephemeral::open_session` instead of sharing it, and the spawn recipe has a third copy (`Process::spawn_piped`); W6 tech debt: one shared guard and one spawn helper. `live::route::unhealthy_refusal` words its message for controls.

**W5 carry-over.** The MCP catalog (`src/mcp/tools.json`, now checked in and shipped) is generated from `public_command()` and `docs/json.md`, neither of which names `__acp`. W5's generator skips every hidden command, and `tests/mcp_contract.rs` asserts that `__acp` and `__worker` appear in no annotation, tool or skip entry (§A22).

**What a NO-GO means.** The hidden command stays as a probe tool; removing it is the owner's call.
