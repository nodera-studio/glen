## Security

### W8-SEC-1: One transcript line with a lone UTF-16 surrogate hides that entry and every earlier entry on the branch

- Severity MED · Status CONFIRMED · W10: no
- Locations: `src/omp/session.rs:145` (parse), `src/omp/session.rs:212` (the branch walk stops at the
  first missing parent).
- Scenario: omp writes strings with `JSON.stringify`, which escapes a lone surrogate as `"\ud83d"`.
  Untrusted text can put one in a transcript, for example in a tool-call argument, an MCP payload,
  or a string truncated mid-pair. omp reads the line back without trouble. serde_json rejects the
  whole line, so glen skips it, and `active_branch` then stops at the missing parent. `show`, `tail`
  and `watch` therefore drop every ancestor of the bad line. The only trace is a "1 malformed lines
  skipped" note, and an injected tool call can use this to hide itself and all the history before
  it from the supervising agent.
- Evidence: a scratch session with a user entry, then an assistant entry containing `"reply
  \ud83d"`, then a user entry. `glen --json show 01a0dddd` returns `skipped_lines:1` and one item
  (the third message only). Node `JSON.parse` reads the same line. In omp, `session-manager.ts:1539`
  calls `stringifyJson`, which is plain `JSON.stringify`.
- Fix: when a line fails to parse, rewrite unpaired `\uD800-\uDFFF` escapes to `�` and retry
  once. Separately, when the branch walk reaches a parent id that is missing because lines were
  skipped, keep the remaining ancestors instead of cutting the branch.

### W8-SEC-2: Spill pruning deletes any regular file older than 7 days in `$GLEN_HOME/out`, including files glen never wrote

- Severity MED · Status CONFIRMED (one of the two merged findings was PLAUSIBLE) · W10: yes
  (`src/output/envelope.rs`)
- Locations: `src/output/envelope.rs:161-173`. The spill name pattern is built at
  `envelope.rs:139`.
- Scenario: GLEN_HOME points at a directory the user already uses. `GLEN_HOME=~` is accepted and
  tested (`glen_home.rs:115`), and the skill tells agents to put GLEN_HOME "under $TMPDIR". If that
  directory already has an `out/` folder, the first oversized output from any command (non-TTY, over
  24000 bytes) silently and permanently unlinks every regular file in `out/` older than 7 days.
- Evidence: reproduced twice. Setup was `out/thesis.txt` and `out/notes.txt` with mtimes set to
  2026-01-01, then `GLEN_MAX_OUTPUT=10 glen doctor --json` (and `glen jobs --json`). glen reports
  `"spilled":{...}`, and afterwards `out/` holds only the spill file. The loop removes every entry
  where `is_file && age > 7d` and never checks the name. docs/design.md:204 documents pruning, but
  only of glen's own spills.
- Fix: prune only names matching `^\d+-[a-z-]+-\d+\.(json|txt)$` that are owned by the current
  uid. Stronger alternative: spill into a subdirectory that glen itself creates.

### W8-SEC-3: An existing GLEN_HOME is trusted without checking its owner or mode, so a pre-created shared GLEN_HOME allows session impersonation, swapping a job's `omp_bin`, and destructive writes through lock-file symlinks

- Severity MED · Status PLAUSIBLE · W10: partly (`src/jobs/lock.rs`, `src/sandbox.rs`,
  `src/rpc/worker.rs` and `skill/glen/SKILL.md` are touched; `src/glen_home.rs` and
  `src/live/registry.rs` are not)
- Locations:
  - `src/glen_home.rs:41-52`: `ensure_dir` creates with mode 0o700 but never stats a directory that
    already exists. The test `existing_root_mode_unchanged` (`glen_home.rs:157`) pins this.
  - `src/jobs/lock.rs:89-93`: `RDWR|CLOEXEC|CREATE` with no `NOFOLLOW`. `lock.rs:37` then runs
    `ftruncate` and `pwrite`.
  - `src/live/registry.rs:45`: any registry is accepted when `session_id` matches and the socket
    path is absolute. `src/live/client.rs:99-103` connects with no peer-credential check.
  - `src/rpc/worker.rs:93` reads `job.json` and `src/rpc/mod.rs:88` spawns `job.omp_bin` from it.
  - The hint "set GLEN_HOME under $TMPDIR" appears at `src/sandbox.rs:76` and `:79`, and at
    `skill/glen/SKILL.md:43` and `:72`.
  - Only doctor checks mode bits (`src/commands/doctor.rs:136`), only on the root, and never
    ownership.
- Scenario: on a multi-user Linux host, the victim sets GLEN_HOME to a predictable shared path
  such as `/tmp/glen`, reading `$TMPDIR` as `/tmp`. Another user created it first with writable
  `run/`, `run/locks` and `jobs/` directories. The attacker can then do three things:
  - (a) Plant a `run/live/<id>.json` that points at their own socket. The victim's `glen send` text
    goes to the attacker, and forged replies come back. The attacker can also plant `inbox` records
    as fake `glen_reply` messages.
  - (b) Rename a new job directory and supply a `job.json` whose `omp_bin` is their own binary. The
    worker then runs it as the victim.
  - (c) Symlink `run/locks/<id>.lock` to a file the victim owns. The victim's next send or control
    truncates that file and overwrites it with lock JSON.
  If the attacker makes the root 0755 and only the subdirectories 0777, doctor stays silent.
- Evidence:
  - (c) was reproduced. The lock was a symlink to `victim2.txt` ("VICTIM2 DATA"), and
    `GLEN_HOME=$S/shared2 ... glen model b7e2d81 fake/fake-2 --json` exited 0. `victim2.txt` then
    contained only `{"v":1,"kind":"control",...}`.
  - A planted inbox record is returned by `glen inbox --json` with no warning.
  - (a) and (b) were confirmed by reading the code only, because no second uid was available.
  - Why PLAUSIBLE: docs/design.md:199 ("glen never chmods a GLEN_HOME that already exists; doctor
    warns about group/other bits") documents the mode policy, and the default `~/.glen` is safe.
    But design.md:455 states that "GLEN_HOME is 0700", and nothing covers ownership or NOFOLLOW.
- Fix:
  - On resolve, `lstat` the GLEN_HOME root and the `run/`, `run/live`, `run/locks`, `jobs/` and
    `inbox/` subdirectories. Refuse with `invalid_env` (exit 2) unless each is a real directory
    owned by `geteuid()` with no group or other write bits.
  - Open lock files with `O_NOFOLLOW` and `fstat` the result (regular file, owned by the current
    uid) before calling `ftruncate`.
  - Change the sandbox hint to a per-user private path, such as the output of `mktemp -d` or
    `$TMPDIR/glen-$(id -u)` created 0700. Also correct design.md:455.

### W8-SEC-4: Control-command spinners print terminal escapes taken from transcript session ids

- Severity LOW · Status CONFIRMED · W10: no
- Locations: `src/commands/ctl.rs:278`, `:281`, `:284` and `:285` interpolate `opened.handle`
  without sanitising it (only the model name at `:282` is sanitised). `src/render/spinner.rs:10` and
  `:19` pass the message straight to indicatif.
- Scenario: a crafted session header id such as `"\u001bc\u001b[31mzz"` is accepted
  (`session.rs:115`), and the handle keeps its control characters. Running `glen --human abort
  <path>` on a TTY prints a raw RIS (terminal reset) and SGR sequence in the spinner, before routing
  rejects the id. The payload is short (about 7 characters, lowercased).
- Evidence: a pty capture via `script -q` shows `stopping 033 c 033 [ 3 1 m`, while the error line
  later prints the same handle as `\x1bc\x1b[31m`. design.md:363 says every string glen did not
  author goes through `render::sanitize`.
- Fix: apply `render::sanitize` inside `Spinner::start` and `Spinner::set_message`.

### W8-SEC-5: `--json` output on a terminal passes raw C1 controls (U+009B CSI) and bidi overrides through from transcripts

- Severity LOW · Status CONFIRMED · W10: yes (`src/output/envelope.rs`, `src/output/stream.rs`)
- Locations: `src/output/envelope.rs:40` (`ColorChoice::Always` for Json and Raw);
  `src/output/stream.rs:25` (same for NDJSON).
- Scenario: a session title or message that contains U+009B or U+202E reaches the terminal raw when
  a person runs `glen --json ls/show/tail -f` interactively, because serde_json escapes only
  U+0000-U+001F. Terminals that honour UTF-8 C1 controls (xterm) execute it. Human mode escapes both.
- Evidence: a fixture title `"X\u009b2J‮Y"` produced `ESC 0  C1(0xC2 0x9B) 1  RLO 1` in `glen --json
  ls --all` under a pty (pretty-printed). `--human` prints `X\u{9b}2J\u{202e}Y`.
- Fix: serialise with a serde_json `Formatter` that also escapes U+007F-U+009F and the bidi
  controls (U+061C, U+200E/F, U+202A-E, U+2066-9) as `\uXXXX`. This is lossless, so apply it always.

### W8-SEC-6: The site deploy fetches wrangler outside the lockfile while CLOUDFLARE_API_TOKEN is in the environment

- Severity LOW · Status CONFIRMED · W10: partly (`.github/workflows/ci.yml` is touched;
  `site/package.json` is not)
- Locations: `.github/workflows/ci.yml:125` (dry run) and `:131-141` (deploy with the token);
  `site/package.json:19-20` (`npx --yes wrangler@4.124.0`). `site/package-lock.json` has no
  `node_modules/wrangler`.
- Scenario: each deploy resolves wrangler's transitive dependencies fresh from the registry. The
  youch and sharp ranges (`cookie ^1.0.2`, `@poppinss/dumper ^0.6.4`, `semver ^7.8.4`,
  `detect-libc ^2.1.2`, ...) are caret ranges, and wrangler ships no shrinkwrap. A malicious patch
  release published within those ranges would run in the job that holds the Cloudflare token. `npm
  run deploy` on the owner's machine has the same exposure.
- Evidence: `rg -c '"node_modules/wrangler"' site/package-lock.json` finds no match. `npm view
  miniflare@5.20260815.0-alpha dependencies` shows the exact pins with caret ranges below them.
  `tests/release_workflows.rs:23` pins the current npx string.
- Fix: add `wrangler: "4.124.0"` to the site's devDependencies so `package-lock.json` locks it with
  integrity hashes. Run `npm ci` in a step without the token, then call the local `npx wrangler
  deploy` with no `--yes` and no version. Update `tests/release_workflows.rs:23` and `:37` to match.

### W8-SEC-7: Release binaries and their checksums are built after third-party actions pinned to mutable refs

- Severity LOW · Status CONFIRMED · W10: partly (`ci.yml` and `flake-proof.yml` are touched;
  `release.yml` is not)
- Locations:
  - `.github/workflows/release.yml:66` (`dtolnay/rust-toolchain@stable`, in the same job as
    `cargo build --release` at `:85` and `package-release.sh` at `:111`).
  - `release.yml:72-78` restores the `~/.cargo/git` cache `omp-git-v1-*`. `ci.yml:33-38` saves that
    cache on main after `dtolnay/rust-toolchain@stable` (`ci.yml:19`) and `Swatinem/rust-cache@v2`
    (`ci.yml:23`) have run.
  - `flake-proof.yml:28` and `:31` use the same refs.
- Scenario: if the upstream branch or tag is compromised, code runs before the compile and can
  swap the binary. `package-release.sh` then hashes the tampered archive, and `install.sh` accepts
  it. README.md:57-58 already says that "the checksum does not prove who published the archive".
- Evidence: every `uses:` reference is a tag or branch, and there is no commit SHA anywhere in
  `.github/workflows`.
- Fix: pin every third-party action to a full commit SHA with a `# stable` or `# v2` comment.
  Optionally add `actions/attest-build-provenance` to the build job.

### W8-SEC-8: `wrap()` turns deeply indented transcript lines into one grapheme per output line

- Severity LOW · Status CONFIRMED · W10: no
- Locations: `src/render/text.rs:65-69` (the indent is truncated to `max-1`) and `:82-88` (the
  indent is repeated on every continuation line). Reached from `render/transcript.rs:43`, the TUI
  (`tui/view.rs`) and `inbox.rs:53`.
- Scenario: a message of 300 spaces (or about 75 tabs) followed by a long run of text prints one
  character per terminal-width line. 100 KB of input becomes 100,004 lines and 20 MB of output (3-6
  s of CPU in a debug build). When stdout is not a TTY, that output is also spilled to
  `$GLEN_HOME/out`.
- Evidence: reproduced at COLUMNS=40 (8 lines of `......…a`) and at COLUMNS=200 (20,300,072
  bytes). Without the indent the same text is 510 lines.
- Fix: cap the carried indent at `min(indent, max/2)`, and drop it when it would leave fewer than
  about 10 columns for content.

### W8-SEC-9: `tail -f` and `watch` re-read and re-hash the whole transcript on every poll that sees an append

- Severity LOW · Status CONFIRMED · W10: no
- Locations: `src/commands/follow.rs:292-296` (the `consumed_prefix_matches` gate) and `:260-279`
  (a full re-read from offset 0).
- Scenario: when following a busy, large session (tens to hundreds of MB), each 250 ms poll after
  an append re-hashes the whole consumed prefix, so the cost is O(file size) per poll for as long as
  omp keeps writing.
- Evidence: on a 202 MB session (debug build), CPU time was 0.01 s over 10 s idle and 6.9 s over 10
  s with one append every 250 ms. The test at `follow.rs:572-611` never checks that a plain append
  avoids the rehash.
- Fix: rely on the inode, size-shrink and tail-4KB checks for every poll, and run the full prefix
  hash only on a slow cadence (every N polls or seconds).

## Error handling

### W8-ERR-1: `glen inbox` prints `ok:true` and `marked_read:true`, then exits 1 when the read cursor commit fails, and the sandbox exit 6 never reaches the caller

- Severity MED · Status CONFIRMED · W10: yes (`src/output/envelope.rs`, `src/commands/inbox.rs`,
  `tests/inbox.rs`, `tests/linux_sandbox.rs`)
- Locations:
  - `src/commands/inbox.rs:275`: `"marked_read":!a.peek&&total>0` is computed before marking.
  - `inbox.rs:289-301`: the `after_output` commit, and `mark_error` at `:21-26`.
  - `src/output/envelope.rs:233`: the ok envelope is written here.
  - `envelope.rs:252-262`: a failed commit turns into `glen: {e}` on stderr and `ExitCode::from(1)`.
- Scenario: `inbox/.read` cannot be written, for example in Codex's workspace-write sandbox with the
  default `~/.glen`, which makes this the normal outcome there. The agent reads `ok:true`,
  `marked_read:true` and acts on the messages. The cursor never moved, so the next `glen inbox`
  returns the same messages again.
- This contradicts the contract in five places:
  - docs/json.md:10: stderr is empty.
  - docs/json.md:16 and :31: `ok:true` applies only to exits 0/10/11/130.
  - docs/json.md:653: `marked_read` means the cursors advanced.
  - docs/design.md:301 and :443: the inbox read marker returns exit 6 `sandboxed` with
    `glen_home_writable:false`.
  - The CI-only `tests/linux_sandbox.rs` `s6_reads_and_inbox` (around `:262-268`) asserts exit 6
    with `details.reason == "sandboxed"` parsed from stdout, which the code cannot produce.
- Evidence: inbox directory set to `chmod 555`/`500` (or `.read` replaced by a regular file):
  - Without a sandbox, `glen inbox --json` prints `{"data":{"marked_read":true,...},"ok":true}`,
    then stderr `glen: cannot mark inbox … read: Permission denied`, and exits 1.
  - With `CODEX_SANDBOX=seatbelt`, stdout is the same, stderr says `cannot write GLEN_HOME (...) for
    inbox inside Codex's sandbox`, and the exit is 1.
  - `tests/inbox.rs:209-217` pins the exit-1 stderr behaviour but never checks stdout.
- Fix: before rendering, when not `--peek`, run `inbox::mark`'s `ensure_dir` plus a probe write. If
  that fails, return the mapped `GlenError` (exit 6 `sandboxed`, or `io`) as the only envelope. Keep
  the commit-after-flush ordering (design.md:201). If the commit still fails after output, print the
  error envelope's message and exit with that error's own code. Update `tests/inbox.rs:209` to
  assert the error envelope.

### W8-ERR-2: A dead job that glen cannot mark lost stays "running" forever: `wait` keeps exiting 10 and prints one raw stderr line per poll

- Severity MED · Status CONFIRMED · W10: no
- Locations: `src/jobs/liveness.rs:131-143` (`report_lost`: `Err(e) => { eprintln!(...);
  observed }`); callers `src/jobs/wait.rs:40` (every poll) and `src/jobs/mod.rs:234` (`jobs`,
  `--active`, control routing). The TUI path (`src/tui/sources/jobs.rs:161-181`) already uses
  `refresh_quiet` and a warning instead.
- Scenario: the worker died, and the job directory cannot be written. Examples: the send was
  escalated but `glen wait` runs inside the Codex sandbox (as SKILL.md:66-71 recommends), or the
  directory is read-only, or `status.lock` is a directory. `glen wait <job> --json` exits 10 with
  `next:"glen wait j…"`, so an agent loops forever on a dead job. Each poll writes one line to
  stderr in JSON mode (about 400 lines over a 90 s wait), and `glen jobs --active` keeps listing the
  dead job.
- Evidence: job forged with `worker_pid 999999` and a job directory set to 0555. `glen wait
  j1234567 --timeout 2s --json` gives `exit=10`, `"status":"running"`, `"ok":true`, and 20-25 stderr
  lines of `cannot mark job … lost: cannot open …/status.lock for writing: Permission denied`.
  Control run: after `chmod 700` the same command exits 7 `job_failed`/`lost`.
- Fix: when `is_lost()` is true but persisting fails, return a terminal `Lost` status in memory
  (with error code `lost`) so that readers report exit 7. Send the write failure through the
  envelope's `warnings` (for example `lost_write_failed`) at most once per process, never through
  `eprintln!`.

### W8-ERR-3: Session controls handle only SIGINT, so SIGTERM or SIGHUP kills glen and leaves the headless omp running and changing the session

- Severity MED · Status CONFIRMED · W10: partly (`src/ctl/ephemeral.rs` and `SKILL.md` are touched;
  `src/jobs/wait.rs` and `src/commands/ctl.rs` are not)
- Locations: `src/jobs/wait.rs:16-28` (`install_interrupt` registers SIGINT only); used by
  `src/commands/ctl.rs:272` and `:551`. `src/ctl/ephemeral.rs:300` starts omp with `process_group(0)`.
  `skill/glen/SKILL.md:67-70` gives shell-timeout guidance only for send and wait.
- Scenario: an agent's shell kills `glen compact <s>` (default deadline 90 s) on a tool timeout
  with SIGTERM (Codex's classic shell kills after 10 s), or the terminal closes and sends SIGHUP.
  glen dies without running `Ephemeral::terminate`, so the omp group survives. omp sees EOF on stdin
  and drains the accepted work (`rpc-mode.ts:2936-2948`), and the compaction lands after the caller
  has gone. The caller gets no JSON, and omp's lease stays held until the drain finishes.
- Evidence: fake_omp with `FAKE_OMP_COMPACT_DELAY_MS=4000`, then `kill -TERM` after 1.5 s. glen
  exits 143, `pgrep` still shows `fake_omp --mode rpc --no-ui --resume …`, and 4 s later the session
  has grown from 11 to 12 lines (`"type":"compaction"`). With SIGINT, glen exits 130 and omp is
  stopped.
- Fix: register SIGTERM and SIGHUP on the same stop flag for control commands (for example
  `install_interrupt_all`, used in `run_control` and `run_models`). Add "give controls a shell
  timeout of at least 100s, or pass a shorter --timeout" to SKILL.md's "Shell timeouts" section.

### W8-ERR-4: A torn inbox or replies line (for example after ENOSPC) swallows the next good reply

- Severity LOW · Status CONFIRMED · W10: no
- Locations: `src/jobs/mod.rs:469-482` (`append_line`: `O_APPEND` plus `write_all`, with no repair
  of a tail that lacks a newline); `extension/glen/index.ts:321` (`appendFileSync`). Readers:
  `src/inbox.rs:56-84` and `jobs/mod.rs:361-367`.
- Scenario: an append that is cut off part-way leaves a fragment with no trailing newline. The next

### W8-ERR-5: Unreadable session files and bucket directories are dropped silently, so show and tail report `not_found` instead of a permission error

- Severity LOW · Status CONFIRMED · W10: partly (`src/omp/handle.rs` is touched;
  `src/omp/listing.rs` is not)
- Locations: `src/omp/listing.rs:51-53` (`let Ok(files) = fs::read_dir(..) else { continue; }`) and
  `listing.rs:91` (`File::open(..).ok()?`); `listing.rs:267-270`; `src/omp/handle.rs:226` and `:241`.
- Scenario: when a session file or bucket is not readable (EACCES), `ls --all` exits 0 without it,

- Evidence: after `chmod 000` on a fixture file, `glen show e27c0de` gives exit 3 `not_found`, and
